# 工作任务管理接入（第一个工作项）

> 目标：把你企微文档里的「工作事项清单」变成一个可签字的交付卡，而不是再写一份周报。
> 状态：链路已打通并在隔离根实测通过（2026-10-28）。IM 双通道里**飞书已通、企微待建通道**，见 §5。

## 1. 它现在能做什么

| 环节 | 落在哪 | 已验证 |
| --- | --- | --- |
| 读清单 | `tools/ingest_workitems.py`（CSV/XLSX → `workitems.v1`） | 33 项测试全绿 |
| 算口径 | 逾期率 / 在办数 / 阻塞数 / 按期闭环率 / 数据缺口 | 单快照实测 66.67% |
| 出报告 | `tools/advisory_to_task.py`（并链 → `runs/<task>/report.json` + 四卡） | `validate_report --require-real` PASS |
| 签字 | `POST /api/tasks/<id>/sign` → `/finalize` | `status=approved`、署名=老板 |
| 展示 | `GET /api/tasks/<id>/delivery` → `crew=c-workops-review 工作任务盘点`（4 步） | 实测返回 |

一次盘点的口径（`tools/ingest_workitems.py:summarize`）：

- **在办** = 状态不是「已完成/关闭」的一切（含阻塞、未知）
- **逾期** = 未完成且截止日早于盘点日
- **逾期率** = 逾期 / 在办；在办为 0 时返回 `null`，不写 0 冒充好成绩
- **按期闭环率** = 完成日 ≤ 截止日的条数 / 已完成条数
- **数据缺口** = 缺负责人 / 缺截止日的条数（评分卡「完整性」维度的证据）

## 2. 从企微文档到签字：三步

### 第一步：把清单落成文件

企微文档 → 右上角「⋯」→ 导出为 Excel（或直接复制成 CSV 存成 UTF-8）。表头认这些说法（大小写/空格不敏感）：

| 语义 | 认得的表头 |
| --- | --- |
| 事项 | 工作事项、事项、任务、事项名称、工作内容 |
| 负责人 | 负责人、责任人、执行人 |
| 截止日 | 截止日、截止日期、计划完成、完成时间 |
| 状态 | 状态、进展、当前状态 |
| 优先级 / 工时 / 阻塞 / 完成日 | 优先级、重要度 / 预估工时、工时 / 阻塞、阻塞原因、卡点 / 完成日、实际完成 |

表头不标准就写一份映射（`field-map`）：

```yaml
source_columns:
  title: 事项名称
  owner: 执行人
  due: 计划完成
  status: 进展
```

缺列直接 rc=2 报错（`数据文件不是...`/`清单缺必填列: due`），不猜不补。

### 第二步：算成快照

```bash
cd JuJing/bot-team
python -B tools/ingest_workitems.py "D:/path/工作事项清单.xlsx" \
  --as-of 2026-10-28 --owner 本人 -o runs/_intake/workitems.json
```

输出里先看 `summary`：`overdue_rate`（逾期率）、`blocked_items`、`worst_three`（逾期最久的三件）。这三个数就是决策卡的证据。

### 第三步：出卡并签字

```bash
# 3.1 起服务时指向工作任务管理包（见 §3）
# 3.2 建单
curl -s -X POST http://127.0.0.1:8787/api/tasks -H "Content-Type: application/json" \
  --data-binary @intake.json      # 中文字段务必放文件里，别用 -d 内联

# 3.3 收敛成报告 + 四卡
python -B tools/advisory_to_task.py --advisory advisory.json --task-id T-20261028-001

# 3.4 签字 + 终态（IM 版见 §5）
curl -s -X POST http://127.0.0.1:8787/api/tasks/T-20261028-001/sign \
  -H "Content-Type: application/json" --data-binary @sign.json
curl -s -X POST http://127.0.0.1:8787/api/tasks/T-20261028-001/finalize \
  -H "Content-Type: application/json" --data-binary @finalize.json
```

`advisory.json` 的最小骨架（`card_kind` 缺省 = attribution）：

- `goal` / `finding[≤2]`（每条带 `factor` + `evidence`）/ `cannot_attribute[≥1]`
- `scorecard` 六维 0–5（**不许全 5**；没人参与一致性判断时 `human_ai_consistency` 必须 0）
- `recommendation[≥1]`（每条带 `action`、`roi.cost/avoided/anchor`、`irreversibility`）
- `decision_log_entry` 六个必填：`id/actor/context/advice/expected_result/verification_plan`
- `sources`（证据文件绝对路径，会拷进 `runs/<task>/data/` 并算 sha256）

## 3. 切行业包（BOT_PACK）

```powershell

```

不设 `BOT_PACK` 就是默认的制造业包。**改前须知**：`BOT_PACK` 一变，同一套 runs 目录里的历史单不会被改写，但新单的 pack 口径（ROI 锚点、crew_id、阈值）随之改变——混跑期间看报告要认 `report.pack`。

## 4. 这套口径的诚实边界

1. **单快照无历史**：第一次盘点只能给「现在什么在烂」，给不出「是不是一直这样」。满 3 次快照后才有 `mean_2sigma` 基线。
2. **清单无依赖/无工时**：区分不了「自己拖」和「等别人」，所以 `cannot_attribute` 里必须写这两条，别假装能归因。
3. **不进 L2 执行**：卡里给的是建议（重排/延期/砍范围/升级），执行仍由你本人做。
4. **T+7 回看**：7 天后用同一份清单复算 `overdue_rate`，那时才谈「建议是否奏效」——这是 `review` 卡的场景，首次盘点不用它。

所以要打通企微，必须先二选一（都需要你动手）：

- **A 扫码绑定**：`octop channel bind --agent JJG00N`（QQ/企微/微信扫码），绑完把通道 id 给我，我把 `notify_im.py` 的 wecom 分支接上。
- **B 给应用凭据**：企微管理后台自建应用的 `corpid` / `corpsecret` / `agentid`（+ 可信 IP 与回调 URL），我按官方「应用消息 + 回调」实现出站与回信。

### 签字经 IM 的身份口径（重要）

IM 里谁点「同意」算谁的签字，必须能落到 signer 白名单（当前 `老板/boss`）。做法：从通道回调里取 `userid`，用一份**本地映射表**（`server/im_signers.json`，不入库）把 `userid → signer` 钉死；映射表里没有的人点同意 → 拒绝并回一句「未授权签字人」。这条不做，IM 签字等于谁都能替你签。

## 7. IM 签字怎么算数（2026-10-28 落地）

签字的问题不是「按钮能不能点」，而是「这个动作能不能追到具体的人、这个人有没有资格、他签的是不是这一版字节」。

三个文件把这件事钉死：

| 文件 | 作用 |
| --- | --- |
| `server/im_signers.json`（不入库，模板见 `im_signers.example.json`） | IM 身份 → signer 的映射。`id` 是应用维度 open_id / 企微 userid，`signer` 必须落在服务端 `--allow-signers` 白名单里 |
| `tools/im_signers.py` | 解析白名单并做**失败闭合**：文件坏了抛错（不放行）、名单为空拒绝所有人、条目 `enabled:false` 拒绝、限定了 `chat_id` 的条目只认那个会话 |
| `tools/im_sign.py` | 白名单 → `GET /api/tasks/<id>` 查状态（已 approved 直接返回 already，不重复签）→ `POST /sign` → `POST /finalize` → 审计旁证 |

三条刻意的设计：

1. **不改 report.json 一个字节**：签字前后 sha256 必须一致，否则「签的到底是哪一版」说不清。实测签名里 `report_sha256` 与现报告哈希逐位相等（`c613f3249813d572…`）。
2. **审计旁证单独落** `runs/<id>/im-sign.json`：IM 身份（掩码）、会话、消息 id、时间、所签 sha、决策号都可回放；旁证不进签名文件，不污染验签口径。
3. **3 秒窗口内只回 toast**：飞书卡片回调有 3 秒上限，签字要跑两个子进程，所以卡片点击后丢后台线程，结果用消息回（失败也回，不许静默）。

卡片上的按钮 `{"action": "sign", "task_id": ...}` 由 `server/notify_lark.py` 生成（`btn()` 支持 action）。回信 a/b/c 与签字是两件事：**a/b/c 记采纳，签字才是对报告负责**——混在一起，采纳率会被「点了按钮」刷高。

实测（隔离服务 8801、隔离 runs）：

```
陌生人           → {"ok": false, "stage": "identity", "error": "未授权签字人"}，且零 API 调用
白名单 + dry-run → stage=dry-run，只读不签
白名单           → stage=approved，decision=D-20261028-001，sha256=c613f3249813d572…
再点一次         → stage=already（幂等，不覆盖前一次签名）
```

## 8. 企微文档能不能直接读（实测结论）

**当前不能**，三条证据：

1. DSH 的 IM 插件是 `@xmanrui/dsh-im@5.7.0`，注册的工具只有 `dsh_im_context / files / source / reply_to / return_file / group_history / group_file`；`grep -riE "wedoc|wedrive|doc_id"` 在插件 `lib/` 零命中 → 它做消息与文件，不做在线文档。
2. IM 历史工具只在「由该群发起的请求」里可用（Web 会话里调用直接报 `Group history is only available during an authorized request from that group`）→ 我这边读不到你在企微群里的归档。
3. octop 的企微连接器只有 `doc/create`、`doc/import`、`doc/search` 三个方法，没有「读单元格」；企微 API 端点本身通（`POST https://qyapi.weixin.qq.com/cgi-bin/gettoken` 返回 200 / `errcode 41004 corpsecret missing`），缺的是自建应用凭据。

**所以走这条路**：企微文档 → 导出 Excel → 直接发给机器人（文件消息，插件能收）→ `ingest_workitems.py` 读它。零权限、零凭据、今天就能用。

如果坚持「直接读在线表格」，需要你给自建应用的 `corpid / corpsecret / agentid` 并开文档权限，我再实测验「智能表格取记录」——**在拿到凭据前我不给结论**，这是没验证的事，不编。

## 9. 飞书能不能当签字身份源（实测结论）

现在**部分可以**，卡在两个权限缺口上（用应用凭据实测）：

| 能力 | 实测结果 | 结论 |
| --- | --- | --- |
| 应用身份发消息 | `tenant_access_token` 拿到、`im/v1/messages` 可用 | 通 |
| 列出机器人所在群 | `GET /im/v1/chats` → `code:0, items: []` | **机器人不在任何群**（或未加群） |
| 读通讯录用户 | `GET /contact/v3/users/find_by_department` → `code:40004 no dept authority` | **通讯录权限未开** |

所以「用飞书权限管理做签字身份」分两步：

- **今天能做的（已做）**：白名单按 open_id 钉死（`server/im_signers.json`），签名可追到人，无法伪造——这是「身份绑定」，不依赖飞书额外权限。
- **要你点两下的**：飞书开放平台 → 应用 → 权限管理里加「获取用户基础信息」（`contact:user.base:readonly`）并设置通讯录可见范围；然后把机器人拉进工作群。之后我可以再加一道「签名前用通讯录校验姓名与部门」，让签名从「一个 open_id」升级成「一个有名有姓有部门的人」。
- 更重的方案是飞书**审批流**（approval v4）：签字=审批实例通过，身份与留痕由平台保证，代价是要建审批定义、多一层配置。个人助手阶段不值得，T1 多人时再上。
