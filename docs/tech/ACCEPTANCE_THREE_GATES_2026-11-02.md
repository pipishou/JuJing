# 验收口径：三关（2026-11-02）

> 缘起：产品负责人 2026-11-02 裁定——**拉绿不是重点**，重点是「能切实可行的使用，能通过代码审查、逻辑校验、案例实测」。
> 本文替代此前「测试全绿＝可交付」的隐性口径。测试绿只是入场券，不是交付物。

## 0. 一句话

**三关全过才算「能用」；任何一关不过，测试全绿也只算自嗨。**

| 关 | 名称 | 回答的问题 | 证据形态 | 谁做 |
|---|---|---|---|---|
| 1 | 代码审查 | 文档承诺的东西，代码里真的有吗？ | 「文档 §x → 代码 file:line → 实现/缺失」对照表 | 独立审查员（非作者） |
| 2 | 逻辑校验 | 状态机、门、接缝会不会自己骗自己？ | 可执行断言（负例必须红）＋调用顺序证据 | 独立校验者 |
| 3 | 案例实测 | 一个真人真数据真模型，能不能从头走到尾？ | 逐步命令 + 返回关键字段 + 耗时 + 缺陷清单 | 用户视角执行者 |

## 1. 关一：代码审查

**判据（全部满足才过）**
- [ ] 审查对象清单明确（哪些文件、哪些规格文档），且审查者未参与该部分编写。
- [ ] 产出「文档承诺 → 实现状态」表，覆盖规格里的**每一个**硬性条款（API、状态、判据、权限），缺失项逐条列出，不许写「基本实现」。
- [ ] P0 缺陷（阻断用户使用的）**清零**；未清零须由产品负责人签字豁免并写明补偿手段。
- [ ] 审查结论带 file:line，可被第三方复现。

**反面样本（一律不算过）**
- 「代码看起来没问题」——没有对照表。
- 只有作者自审（同源自审有结构性上限，见 jujing-agent-workflow 公理 2）。
- 只审新代码、不审接缝（新旧之间最容易断）。

## 2. 关二：逻辑校验

**判据**
- [ ] 每条门/判据都有**负例**：故意造假（删字段、置 None、改字符串形状、跳状态）必须被拦；负例不红＝门是假的。
- [ ] 状态机无跳步、无回退漏洞，重复提交幂等，并发写有防护（锁/原子写/发号器）。
- [ ] 关键调用顺序有证据：例如「先覆盖 report 再校验」这类顺序错会让校验永不触发——必须验证**校验读到的是提交时的那份字节**。
- [ ] 事件与账本不双写打架：同一事实只有一个事实源，其余是投影；投影可由事件重放。

**已知要盯的三处（历史欠账）**
1. `core/gate.py::_apply_to_report` 回写 confirmed gate 是否丢 `action`。
2. `tools/finalize_delivery.py` 是否先 `apply_gate_view` 覆盖 report 再跑 F28（若是，F28 永不触发）。
3. `core/gates.py` 中「空 action 放行」与「伪造 action 拦截」的边界是否可被利用。

## 3. 关三：案例实测

**判据**
- [ ] 真实数据（不是 demo、不是 fixture）：本轮用 `D:/work/文档类/企业管理部/工作事项/企业管理部工作事项-20261026.xlsx`。
- [ ] 真模型（`core/llm.py` → opencode-go / deepseek-v4.1-flash / reasoning high），不是手写 JSON 冒充 AI 产出。
- [ ] 全链路：账本 → 建单 → 产出 → 封存 → 签字 → 定案 → 交付视图（→ T+7 回填）。
- [ ] 每步留证据：命令、返回关键字段、耗时；失败也算证据，但要写清是产品缺陷还是数据缺陷。
- [ ] 隔离：临时端口 + `BOT_RUNS_ROOT`/`BOT_LEDGER_ROOT`/`BOT_WORKITEMS_FILE`/`BOT_EVENTS_FILE` 指向 `_tmp_*`，不污染真实账本。
- [ ] 结论必须回答一句话：**「这套东西今天能不能给我自己每天用」**——能/不能，卡在哪一步。

**反面样本**
- 用 `tests/fixtures/*` 跑通→不算实测。
- 用手写的 advisory JSON 跑通→只证明管道通，不证明 AI 有用（必须单独标注）。
- 「跑通了但我不敢用」→ 等于没过。

## 4. 三关与 M0–M7 的关系

- M0–M7 是**实测期间的度量**（有没有真对话、有没有真提醒、有没有真签字、有没有回填），不是替代品。
- 三关是**交付门**；M 判据是**运行质量指标**。门不过不谈指标；指标不涨说明产品没价值。
