# 技术路线体检 · bot-team 第一版

> 日期：2026-10-30｜形态：存量演进（本地 `bot-team` 仓库，分支 `bot-team`，HEAD `add5c1d`）
> 阶段：③开发前技术评审（G0 前）｜范围：技术路线、框架取舍、服务边界、契约、可迁移性
> 依据：用户「先做技术体检，现在我们有 octop（查看是否有新版）、dsh 两个框架」
> 结论：**不换框架；采用本地优先的模块化路线；Octop 只做 T1 适配，DSH 只做开发/内部生产工具。**

## 0. 一句话结论

当前 `Python 标准库 HTTP + JSONL + 本地文件 + 静态 UI` 的栈对“单用户、本地、先自用”的第一版是合适的；真正要修的是 **183 KB 单体、缺失的依赖清单、未定义的角色/插件契约、分散的 LLM 调用**，不是“框架不够高级”。

## 1. 取证

| 项 | 事实 | 影响 |
|---|---|---|
| 服务单体 | `server/app.py` 183,574 bytes / 4,063 行 / 142 个函数 / 6 个类 / 16 个 `/api/*` 路径 | 加 5 角色 + A/B 路由 + 插件后会继续膨胀，难定位、难测试 |
| 测试基线 | 29 个 `tests/test_*.py`；`test_core_m15.py` 188 项；`test_mvp_gate.py --selfcheck` 1 正控 + 10 负控 PASS | 有回归资产，重构可保护行为 |
| 依赖清单 | `requirements.txt` / `pyproject.toml` / `package.json` 均缺失 | 换机/迁移不可复现；Python 3.12.13 + PyYAML 6.0.3 只存在于口头/venv |
| 模块种子 | `core/` 已有 eventlog、reminders、dialog、scene、gates、llm、octop_client 等；`server/services/` 只有安装脚本 | 适合“原地拆”，不是从零重写 |
| 角色/插件 | `packs/*/pack.json` 有行业包；但无统一 role/plugin schema | 第一版产品主线就是角色 + 插件，契约必须先定 |
| Octop | 安装 `v1.0.3b1`；PyPI 稳定版 `1.0.2`，预发布最新 `1.0.3b1` | 当前已是 PyPI 最新预发布，**无更新版**；不升不降 |
| DSH | 桌面 Harness（`D:\tools\deepseek-harness`，Electron），提供 skill/workflow/subagent | 是开发/内部生产环境，不是产品服务端运行时 |

## 2. 三条路线

| 路线 | 一句话 | 证据 | 成本 | 风险 | 可逆性 |
|---|---|---|---|---|---|
| **A 本地优先模块化（推荐）** | 保留 stdlib 服务与 JSONL，拆单体、定契约、加 LLM 网关；Octop/DSH 只做适配/开发工具 | 现有 29 个测试、core 模块齐全、单用户场景明确 | 3 个 PR 起步；1–2 天评审 + 1–2 周拆分 | 拆分期间行为漂移；契约设计过度 | 双向；可随时收窄 |
| **B Octop 承接** | 把产品迁到 Octop（FastAPI/JWT/IM/cron/专家包） | Octop 1.0.3b1 已有用户/渠道/知识/用量；T1 需要这些 | 重写服务层与 UI 适配；数周 | 多用户/IM 过重；专家包与当前 `manufacturing` 命名漂移；升级跟随成本 | 双向但返工大 |
| **C DSH 承接** | 用 DSH Agent Teams/workflow 做产品运行时 | DSH 有 5 角色/ workflow/tape 能力 | 需自建服务、鉴权、状态、UI | DSH 是桌面 harness；Agent Teams 实验性、共享 cwd、无多租户 | 双向但产品边界会被工具绑死 |

**MECE**：A/B/C 按“产品运行时归属”分，互斥；已知缺口＝纯咨询/交付服务，归 B 阶段，不在第一版。

## 3. 决策

**选 A：本地优先模块化。**

- 产品只保留 **一个运行时**：本地 Python 服务 + 内部 worker；
- DSH 只做 **开发/内部生产工具**（skill、workflow、会话回放），不嵌入产品；
- Octop 只做 **T1 适配器**（多用户、IM、定时），通过端口/适配器接入，不迁主栈；
- 这样既保住“单用户先跑通”，又不把未来锁死。

**为什么不是 B/C**：

- B 解决的是 T1 才需要的问题（多用户/渠道/权限），现在做会把第一版拖成平台；
- C 解决的是“开发时怎么编排 agent”，不是“产品怎么稳定服务一个人”；
- 两者都可以在 A 的端口后面接，不需要现在换底座。

## 4. 七个 ADR（详见 `docs/tech/ADR-*.md`）

| ADR | 决策 | 关键理由 |
|---|---|---|
| ADR-001 | 运行时：单机服务 + 内部 worker；不引入 agent 框架 | 单用户、本地、可调试；框架不解决当前瓶颈 |
| ADR-002 | 服务拆分：`server/http` + `server/api` + `server/services` + `server/workers` | 183 KB 单体是当前最大工程风险 |
| ADR-003 | 状态：JSONL + 快照 + schema 版本 + 单写锁；暂不上数据库 | 保留审计/可回放；单用户量级足够 |
| ADR-004 | 角色/插件契约：`role.yaml` / `plugin.yaml` / 事件 / 工具权限 | 第一版产品主线；契约晚定必返工 |
| ADR-005 | LLM 网关：统一 provider/model 策略、超时、重试、成本、prompt 版本 | 现在调用分散，无法算账/换模型 |
| ADR-006 | UI/API：保留静态 UI + `/api/v1` + SSE；本地绑定；管理者访问才加 token | 不重写 React；先保第一屏 |
| ADR-007 | 可复现：`pyproject.toml` + Python 3.12 固定 + 测试入口 + 迁移清单 | 换工作电脑必须可复现 |

## 5. 风险与失效边界

| 风险 | 触发信号 | 处置 |
|---|---|---|
| 单体继续膨胀 | `app.py` > 5,000 行或新增 3 个以上路由组 | 立即执行 ADR-002 的拆分切片 |
| 契约漂移 | 角色/插件字段在代码与 YAML 不一致 | schema 校验 + 负测试；契约变更走 ADR |
| 状态损坏 | 并发写/进程崩溃后 JSONL 半行 | 单写锁 + 原子 rename + 快照回放 |
| LLM 成本/延迟失控 | 单次会诊 > 60s 或成本不可查 | 网关限流/超时/降级；记录 token/费用 |
| 管理者访问暴露 | 8787 绑定 0.0.0.0 且无鉴权 | 默认 127.0.0.1；对外必须 token + 反代 |
| 框架跟随成本 | Octop/DSH 升级破坏适配 | 适配器隔离；升级前跑契约测试 |
| 绿测掩盖死功能 | 测试绿但 14 天无人用 | 以使用信号为准，不以测试绿代替产品验证 |

**失效边界**：如果 2 个月内必须上 T1 多用户/IM，提前启用 Octop 适配器；如果真实数据量超过 JSONL 可维护范围（例如 >10 万事件/月），再评估 SQLite/Postgres；如果 5 角色需要跨机执行，再评估分布式编排。
