## 1. 文章要点（事实层，非评论）

作者 5 天做了这些事：
1. **品牌 VI / UI 组件库 / 100+ 页 PPT 模板** → 全部打包成 Skill（「虚实PPT Skill」「设计组件 Skill」），供全员复用。
2. **自建企业中台**（飞书工作台入口替换成自己的域名，权限复用飞书登录，数据底层来自飞书多维表格，实时同步）。
3. **应用 tab**：员工用 Claude/Codex Vibe Coding 的应用，通过「把中台包装成 MCP」→ 复制一段 Prompt 给 Agent → Agent 自动部署到公司服务器、自动分配子域名（`aaa.virxact.net`）、自动问权限范围（仅自己/指定同事/全员）、按账号 ID 隔离。
4. **Skill tab**：上传即发布；平台检测本地与平台版本不一致会提醒更新。
5. **资料 tab**：承载 VI/组件库/PPT 等公司资产。
6. **首页千人千面**：右下角「改我的首页」→ 发一段话给 Agent → Agent 读 MCP 按品牌规范生成个性化首页，绑定账号 ID；不会用 Agent 的人几乎寸步难行。
7. **OKR 可视化面板**；所有多维表格与数字数据由 Agent 维护，人工录入的错误被 Agent 推演规则 + 异常清单清理。
8. 价值观：事务性机械工作不让人做；「让员工适应系统」→「系统适应每一个活生生的人」。

**它的本质**：不是「聊天框」，是**组织级 Agent 操作中台**——入口=飞书，权限=飞书，数据=飞书，部署=MCP，资产=应用/Skill/资料，个性化=Agent 改首页。

## 3. 对齐 / 差距矩阵

| 文章中台的构件 | 我们有对应物吗 | 判断 |
|---|---|---|
| 组织身份 + 权限（复用飞书） | ❌ 单用户「老板」 | **P0 地基** |
| 应用部署/隔离/子域名 | ❌ 本机单实例 | **P0 地基** |
| 应用广场（上架/权限/分享） | 部分：员工/班组/货架，但没有「安装/版本/可见性」 | P1（标品差异点） |
| Skill 市场（上传/版本/分发） | 部分：pack/判据/角色 persona 可打包，无版本分发 | P1 |
| MCP 作为集成/部署契约 | ❌ | **P0/P1 最便宜的生态入口** |
| 数据 = 组织数据源（飞书多维表格） | 部分：CSV/XLSX 上传；无同步 | P1（制造业多半是 ERP/MES/Excel） |
| 千人千面首页 | 部分：四区固定 | P2（非阻塞） |
| 员工/班组编排与运行态可视化 | ✅ 我们更强（舞台/事件流） | 差异点 |
| 交付可信（签字/审计/回看） | ✅ 我们更强（文章中台没有） | **护城河候选** |
| OKR/用量面板 | ❌（有 cost 记录，无 per-user 账本） | P2 |

**判断**：文章验证了「组织级 Agent 中台」的需求真实存在，但它做的是**通用容器**（应用/Skill/资料/首页），我们做的是**能交付结果的一支 AI 班组**。二者不是竞争关系：我们应当成为别人中台里的「AI 员工部门」，而不是再抄一个中台。理由：通用中台在飞书/钉钉/大厂射程内，且作者的平台是自用、不售卖；而「制造业归因 + 可签字交付 + 审计回看」是通用中台不会做的深水区。

## 5. 权衡

- A 不能停：真实制造业数据与「是否 5 分钟出结论 / 是否愿签 / 7 天是否复用」的反馈，是后面一切的地基；没有它，B/C 都是猜。
- D 是最便宜的组织级入口：MCP server（tasks/run/report/sign/team/pack）+ DSH 插件，2–3 周可换「别人怎么把 bot 团队接进自己的工作流」。
- B 是标品地基，但先要定「组织是谁」；否则会做成两套（自用单租户 vs 对外多租户）都半拉。
- C 是变现，但需要第二行业样本证明「通用判据 + 行业包」不是伪通用；过早做市场会变成空货架。
- E 明确不做。

## 6. 推荐（置信 MED-HIGH）

**顺序：A + D 并行（2–4 周）→ B（组织定了之后 4–6 周）→ C（有付费/第二行业信号后）**；不做 E。
具体：本轮批次收口后，先让用户用真实数据跑 2–3 单（个人验证），同时并行做 D（bot-team MCP server + DSH 插件骨架，复用现有 8 类 API），再据「组织是谁」决定 B 的身份层（飞书 SSO 单租户 vs 多租户 SaaS）。

置信 MED-HIGH 的理由：需求真实性有文章与亲身两个证据；不确定性集中在「谁付费、哪个组织先用」。

## 12. 评论证据与方案修订 v1.1（2026-10-20，用户补 4 条高价值评论 m01188–m01191）

### 12.1 四条评论逐条读解

**C1 梦小天幼（69 赞）：项目即机制 + 中间层 UI + 双飞轮**
> 「把日常思考通过 AI 层转录，以项目为机制，项目里有目标、待办、想法、沉淀、参考、数据；有一个中间层 UI 呈现 AI 理解后的效果；AI 每次记录、我的每次反驳都有数据留档；每隔一周，AI 根据历史数据对提示词进行修正。」
- **验证**：与我们「runs/<task_id> + 决策日志 + WAL + pack 判据 + 四区工作台」同构；他说的「最简单飞轮」= 我们的「记录→复盘→修正判据/提示词」。
- **我们缺的**：①没有**周级自动/半自动修正**（现在只有批次结束手写回执，驳回理由未系统汇总）；②「反驳留档」虽有 decision_log/cannot_attribute，但没有把「高频被驳回的原因」回灌成 prompt/判据增量；③缺少「提案→人批准→生效」的补丁通道。
- **动作**：新增 B13 周级飞轮（1 周）：`tools/weekly_review.py` 扫 `runs/*/loop/` + decision_log + cannot_attribute + 既有 patch，产出 `weekly-<date>.md`（命中/证伪/高频驳回理由/建议 prompt+判据 diff 草案）；人批准后写 `packs/manufacturing/pack.prompt_patch.json` 与 persona 增量。红线：**只提案不自动改**，补丁必须可回滚（版本号只进不退）。

**C2 比比@小声比比（22 赞）：自上而下封装最佳实践，自下而上需全员能力**
> 「自下而上需要大家 AI 能力都强、主动性高；我改造公司是自上而下——核心层把核心组件和重要工作流封装好，再让其他人复用（公司最佳实践良莠不齐，理论上只应复制最好的实践）；通过打通各种 CLI，让公司每个角落的数据/会议/信息自动到达看板；下一步归因、决策、分析；未来让 AI 参与管理甚至对每个人绩效打分。」
- **验证**：我们的 `core/` 通用件 + `packs/` 判据 + 班组模板 = 「封装最好的实践」；交付卡里的归因/建议/决策日志正落在他的「下一步」。他的「只复制最好的实践」给我们一条治理条款。
- **风险/边界**：绩效打分不做（信任、合规、单向门；也超出「交付可信」护城河）。
- **动作（治理条款，写入架构/验收）**：G1 判据与班组包只能从 core/pack 的「已验收版本」发布，禁止分队自造判据绕过 pack（与「不可自签」同级）；G2 数据进看板只读 + 必须带 provenance/出处。

**C3 Roger（10 赞）+ Ryan 追问 + Roger 回复：通用「员工自建应用」的反例（最强反证）**
> 「半年前内部就这么干，很快发现每个人做出来的应用模块质量差别巨大，尤其非技术人员连数据该放哪、密钥怎么放都搞不清。最后停掉了所有内部应用，改成 Agent 可参与协作的内部看板 + 多维表格；不该沿用传统 ERP 的模式做一堆界面，而是实时生成交互式 HTML 和图片。」Ryan：「肌肉记忆——熟悉闭眼点的页面 vs 每次重新阅读理解的页面，操作者更喜欢哪个？」Roger：「报告类 Skill 稳定后，每次生成一致性很好；临时需求才自然语言按需生成，要什么给什么，不是一个大 Dashboard。」
- **结论（对方案有实质修改）**：
  1. **通用应用广场/员工自由建应用 = 已证伪路径**（质量参差、密钥与数据位置失控）→ 我们 D2 负边界「不做通用应用中台」从判断升级为**有第三方实证的反证结论**。
  2. **主界面固定版式（肌肉记忆）+ 局部生成**：四区工作台、交付卡骨架必须稳定；生成只发生在交付物内部（文字/图表），且生成结果**落盘为可复现产物**（reproducible artifact），不做「每次重生成首页」。这一条直接影响 M2/M3 的 UI 路线。
  3. **密钥/数据/权限平台托管**：班组包与判据包**不得携带凭据**，凭据只由 server/core 注入 → 新增红线 G3。
- **顺带支持 D（MCP）**：他说「Agent 可参与协作」，正是我们 server MCP 化的场景。

**C4 安康说AI（山东）：开发脚手架 + 开发 Skill + 平台托管能力**
> 「平台有开发脚手架（TS 服务端 + MCP、vue/react 前端），脚手架还提供一个开发 skill，指导本地智能体快速接入平台能力（OCR、大模型调用、文件存储、权限），开发完成后通过 skill 带脚本自动发布；数据库/应用/权限由平台托管。新手四个问题：1 怎么发布托管应用 2 怎么存数据（不懂数据库）3 上传文件怎么存储/使用/预览 4 怎么对接大模型、哪申请 key。」
- **验证**：我们缺的正是「**员工/班组包作者工具**」——现在新增一个员工或班组要手改三套 YAML + persona + 判据，非技术业务专家做不了；平台托管能力（模型 key/文件/权限/审计）我们也只有一部分。
- **动作**：新增 B14 员工包脚手架（作者工具，约 2 周）：`tools/scaffold_member.py`（生成 preset.yml + persona.md + skills/SKILL.md + sample.md/png + manifest.json 并校验）、`tools/publish_pack.py`（版本化 + changelog + 校验 + 注册到货架 coming→craft→active）、配套 `skills/author-bot-member/SKILL.md`（给 AI 的开发说明书，等价于他的「开发 skill」）+ 能力托管清单（模型凭据注入、文件存储、权限、审计）落 server/core。

### 12.2 合并后的产品定位（修订）

> **不做**通用应用中台；**做**「受控的 AI 员工/班组部门 + 固定版式工作台 + 平台托管能力 + 受控扩展（包/MCP）」。
> 一句话差异：文章的中台让**每个人造自己的工具**；我们让**一支班组交出可签字的结论**，且最好地实践只从平台发布。

## 13. 拍板：三台阶升格（2026-10-20，用户 m01213）

> 用户原话：「由自己用-公司团队用-标品，三个台阶升格」——即承重追问的③（两者），并显式拆成三台阶，排除「一步到位做多租户 SaaS」。

### 13.1 三台阶与升格判据

| 台阶 | 谁在用 | 形态 | 完成定义（升格门槛，可机检为主） |
|---|---|---|---|
| **T0 自己用** | 老板本人 | 本机 8787 单用户，数据上传，交付卡签字+回看 | 连续 2–4 周真实使用 ≥6 单；签字率≥80%；7 天回看有复用；每周省≥5h；P0 事故 0 |
| **T1 公司团队用** | 自己公司 3–5 人 | 单组织内网：SSO 复用 + RBAC + 任务归属 + 组织数据源只读 + 审计/成本账 + MCP | ≥3 名非本人用户每周用；≥50% 任务由他人发起；交付物被转发/进会议；「退回去会难受」 |
| **T2 标品** | 外部制造业团队 | **私有化交付优先**（镜像/安装器/升级回滚），SaaS 后置；行业包版本化+作者工具+license | ≥2 家不同公司付费；第 2 行业包跑通；单客户交付≤2 人日；续费/复购信号 |

### 13.2 每台阶只加「升格必需件」

- T0：B13 周级飞轮 + 真实 2–3 单（把「记录→复盘→补丁」跑起来）。
- T1 最小前置（只三件，1–2 周）：①身份抽象 `owner → actor/role`（signer 白名单角色化，不改 API 形状）；②任务归属（`created_by/assigned_to` 落 task.json 与 runs）；③部署/备份/审计脚本（systemd 或 docker-compose + 每日备份 + 审计日志导出）。**不做** K8s、不做多租户、不做计费。
- T2 前置：D2 脚手架 + 包版本化 + 私有化安装器 + 第 2 行业包（建议 8D/S4 之外选客诉 8D 或停机 OEE，视客户数据）。

### 13.3 关键决策（写入架构）

1. **T2 先私有化、不先 SaaS**：制造业数据主权与内网现实；SaaS 是第 3 台阶之后的可选形态。
2. **T1 身份复用组织现有 SSO/IM**，不自建身份体系；无 SSO 则本地账号 + RBAC（双向门，先适配器后实现）。
3. **单分支 + 配置开关**（`deploy=local|org|private`、`tenant/role`），拒绝三套 fork。
4. **升格判据可机检**：runs/status/signature 已能统计单量、签字率、复用；B13 周报自动出「升格仪表盘」。

### 13.4 反证信号（每台阶的刹车）
