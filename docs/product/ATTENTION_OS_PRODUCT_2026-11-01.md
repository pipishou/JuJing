## 0. 一句话

> **不是再给你一个 AI，而是替你管住 4–5 个 AI 的注意力控制面：任务可以并行，你的注意力不并行。**

---

## 1. 为什么要改

你现在的真实状态：

- 同时开 4–5 个 AI 任务，每个都要你喂上下文、看进度、做判断
- 任务之间来回切换，时间被切碎，精力在“重新进入状态”上耗尽
- AI 越多，越像一个需要你管理的项目组合，而不是替你省时间

现有 bot 团队如果只是再加一个“AI 班组”，会犯同一个错：**增加一个需要你关注的对话窗口**。

真正要解决的不是“任务不够多”，而是：

> **任务并行度上去了，注意力并行度没上去。人是瓶颈，不是模型。**

---

## 2. 产品定义

### 2.1 旧定义

> 一个每天陪你管工作的 AI 班组。

### 2.2 新定义

> **一个替你管住多个 AI 任务的注意力代理。**
> 它让任务继续跑，只在“值得你出现”的时候叫你；其余时间它替你等、替你收、替你记。

三个承诺：

1. **同一时刻，只让你看一个需要你决定的问题。**
2. **每天主动打扰有预算，默认不超过 3 次**（可调；单向门不受限）。
3. **所有任务都有归宿**：推进 / 等待 / 停泊 / 放弃，不靠你记。

### 2.3 它不是什么

- 不是又一个聊天工具
- 不是通用 Agent 平台
- 不是自主写代码的 coding agent
- 不是把 5 个角色同时塞进一个对话框

---

## 3. 核心洞察：注意力是预算，不是态度

### 3.1 注意力单位

把一次打断粗略记为 **5 分钟**；一次上下文切换记为 **15 分钟**（重新进入状态）。数字先作为可观测初值，后续用自己的数据校准。

### 3.2 打断公式

```text
打断价值 = 影响 × 紧迫 × 不可逆系数 / (切换成本 + 不确定成本)
```

只有满足下面任一条件，才允许主动打断：

| 条件 | 例子 |
|---|---|
| 单向门 | 要发布、要删数据、要花钱、要对外承诺、要改权限 |
| 被用户卡住 | 没有你的输入，任务无法继续 |
| 硬截止 | 今天/明天到期，且不处理会损失 |
| 高影响决策就绪 | 选项、推荐、成本、反悔代价都已备好 |

其余一律：**进队列、进日报、进周报，或直接按 mandate 自己走。**

### 3.3 沉默也是推进

- 在授权范围内，bot 自己推进，只写账本，不报告“我正在做”
- 没有状态变化，不发“还在跑”
- 用户说“继续”，直接做下一步，不再确认
- 只有“做完 / 卡住 / 需要拍板 / 触发单向门”才出现

---

## 4. 五个核心对象

| 对象 | 一句话 | 关键字段 |
|---|---|---|
| **Work Item** | 一件要推进的工作 | id、标题、来源、状态、影响、紧迫、可逆性、WIP 槽位、下一步、下次回看 |
| **Attention Ticket** | 一次需要你出现的问题 | 只含一个问题、2–3 选项、推荐、成本、截止、反悔代价 |
| **Mandate** | 授权凭证 | scope、strength（observe/accept）、policy_version、sender、expires |
| **Subscription** | 上下文包 | 任务背景、证据、历史；**不授予权力** |
| **Attention Event / Budget** | 注意力账本 | 打断、停泊、批处理、决策、切换、用户评价 |

> 关键分离：**Mandate 是权力，Subscription 是上下文。**
> 收到上下文，不等于获得授权；授权必须单独签发。

## 5. 用户旅程

### 5.1 早上 3 分钟

打开飞书，bot 只发一条：

```text
今天需要你出现的 3 件事：
1) 【拍板】品质巡检异常归因：A/B 两个方向，推荐 A（10 分钟）
2) 【输入】补料率数据缺 3 天，需要你确认是否可用（2 分钟）
3) 【知会】其余 4 件已停泊/推进，最早明天再找你
```

不是 10 条通知，不是 5 个 agent 抢话。

### 5.2 白天

- 默认静默；bot 在后台推进
- 只有四类打断（见 3.2）
- 你发 `/focus 90`，进入 90 分钟免打扰；只有单向门能穿透
- 你发 `/queue`，看完整队列；可以 `/park`、`/resume`、`/defer`

### 5.3 晚上 2 分钟

- 批量处理当天剩余决策
- 对每个打断给一个“值得/不值得”反馈（一个按钮）
- bot 把反馈写进注意力账本，第二天调整阈值

### 5.4 每周 10 分钟

- 一张周复盘卡：完成了什么、停泊了什么、打断了多少次、救回多少时间、下周只保留 3 个重点
- 明确回答：**这周 AI 是帮你省了注意力，还是又开了一个战场？**

### 5.5 当你又开第 5 个 AI 任务

bot 不接“再加一个”，而是问：

```text
现在有 4 个活跃任务，超过上限 2。
要接这个新任务，必须停泊一个：A 品质巡检 / B 补料率 / C 周报 / D 新任务？
```

这就是产品在替你做**注意力调度**，而不是替你堆任务。

## 6. 角色重定义

| 旧 | 新 |
|---|---|
| 5 个角色在一个对话里轮流说话 | **团长 = 唯一前台；5 席位 = 被调用的能力** |
| 团长也做分析 | **团长只路由、裁决、收口，不做具体技术判断** |
| 每个任务都在同一个上下文里 | **每个 Work Item 一个 worker 会话，独立上下文/产物** |
| 用户是项目经理 | **用户只做决策与授权** |

### 团长（Attention Router）职责

1. 接住来源（飞书、文件、其他 AI 任务、日历）
2. 判断：忽略 / 观察 / 停泊 / 派工 / 开票
3. 维护 WIP 与注意力预算
4. 在需要你时，只递一个 **decision-ready** 的问题
5. 收口 worker 的六行 handoff，不搬运全文

### Worker 职责

- 一个 Work Item 一个会话
- 自己读证据、跑工具、写产物
- 只回传六行：目标 / 结论 / 证据 / 风险 / 开放问题 / 下一步
- 不直接打扰用户；需要拍板时交给团长开票

## 7. 交互契约（飞书）

### 7.1 命令

| 命令 | 作用 |
|---|---|
| `/today` | 今天 3 件事 + 当前 WIP + 预算 |
| `/next` | 只给下一个最值得做的事 |
| `/queue` | 完整队列（含停泊/等待） |
| `/focus 90` | 90 分钟免打扰 |
| `/park <id>` | 停泊一个任务，释放 WIP |
| `/resume <id>` | 恢复一个停泊任务 |
| `/mandate` | 查看/签发今天的授权 |
| `/brief` | 一页决策简报 |

### 7.2 主动消息格式

每条主动消息必须是一张票，而不是一段汇报：

```text
【需要你拍板】品质巡检异常归因
问题：本周退货率上升，先查机台还是先查产品型号？
A. 先查机台（证据强，2 天）
B. 先查型号（覆盖广，3 天）
推荐：A；反悔成本：低
截止：今天 18:00
```

没有选项、没有推荐、没有截止的，不许发。

### 7.3 打扰预算

- 默认 3 次/天；`/focus` 内 0 次（单向门除外）
- 连续 3 天“不值得”评价 → 自动降频
- 用户说“别烦” → 当天只留单向门
- 预算不是硬上限：单向门永远可以穿透

## 8. 指标：注意力 ROI

### 8.1 主指标

| 指标 | 定义 | 两周目标 |
|---|---|---|
| `wip` | 同时活跃任务数 | ≤2 |
| `interrupts/day` | 主动打扰次数 | ≤3 |
| `decisions/day` | 需要用户拍板次数 | ≤3 |
| `context_switches/day` | 用户主动切换任务次数（自报/事件） | ≤5 |
| `decision_latency` | 从开票到拍板的中位时间 | ≤10 分钟 |
| `attention_minutes_saved/day` | 自报节省 − 实际花费 | >0 |
| `ticket_worth_it` | “值得”占比 | ≥70% |
| `missed_one_way` | 漏掉的单向门 | **0** |

### 8.2 反虚荣指标

以下数字不作为成功证据：

- 发了多少条消息
- 有多少个 agent/角色
- 跑了多少 token
- 建了多少任务

它们只能说明“系统很忙”，不能说明“你更轻松”。

### 8.3 主观负荷

每天一个 1–5 分：“今天 AI 让我更轻松还是更累？”
连续 3 天 ≥4，自动降频并复盘。

## 9. 方案取舍

| 选项 | 一句话 | 成本 | 风险 | 门 |
|---|---|---|---|---|
| **A 在 bot-team 内加注意力层** | 复用事件流、飞书、gate、UI | 1–2 周 | 旧代码耦合 | 双向 |
| B 独立注意力路由应用 | 干净，但要重做入口/状态 | 3–4 周 | 重复建设 | 双向 |
| C 直接跑 superagent | 现成治理实现 | 高 | 要升 DSH、单仓库、danger-full-access | **单向** |
| D 维持现状 | 继续 4–5 个窗口 | 0 | 精力继续被切碎 | — |

**推荐：A，置信 HIGH。**
理由：痛点已被用户明确；现有 bot-team 已有事件流、飞书入口、gate、签字和周报；注意力层是增量，不是重写。C 不碰：它是单 GitHub 仓库的 coding agent，且本机 DSH 版本不满足，升级是单向门。

**不做什么：**

- 不增加可见 agent 数量
- 不做自主 coding / 自动发布
- 不做“每条消息都推送”的实时播报
- 不把 superagent 装进产品关键路径

## 10. 与 MVP v1.1 的关系

M0–M7 继续有效（真实使用窗口、对话、提醒、裁决、签字、T+7、零卡死、命中率）。

新增注意力层：

| 编号 | 判据 | 负测试 |
|---|---|---|
| A0 | 有注意力账本与基线（打断/切换/决策） | 无事件 → 红 |
| A1 | WIP ≤2；第 3 个活跃任务必须停泊 | 强行第 3 个 → 红 |
| A2 | 打扰 ≤3/天；focus 内 0（单向门除外） | 第 4 条主动消息 → 红 |
| A3 | 每张票只有一个问题、有选项/推荐/截止 | 无推荐 → 红 |
| A4 | 每周注意力 ROI 回看；连续 3 天“更累”降频 | 无回看 → 红 |

## 11. 风险与失败信号

| 风险 | 表现 | 对策 |
|---|---|---|
| 假紧迫 | 什么都说是单向门 | 单向门清单 + 用户一键“不值得” |
| 藏事 | 重要任务被停泊太久 | 队列老化提示；每天显示停泊数 |
| 过度批处理 | 错过时机 | 硬截止可穿透预算 |
| 授权滥用 | 在 observe 之外执行 | mandate gate + 负测试 |
| 指标作弊 | 只报“省了时间” | 事件 + 自报 + 周复盘三方对账 |

**14 天失败信号：**

- 连续 3 天不打开 `/today`
- 打断 >5 次/天，且“不值得”>30%
- 队列 >10，且没有停泊/放弃动作
- 你觉得“用它比不用更累”

失败就降级回“只做周报”，不硬撑。

## 12. 下一步

1. 用当前 4–5 个 AI 任务做 3 天基线（只记录，不改变行为）
2. 实现 A0–A2：账本、WIP、日报、票、focus
3. 再用**个人工作任务管理**首单验证：连续 3 个工作日，一次真实任务是否能在 ≤3 次打扰内完成
4. 通过后再上 A3–A4（mandate、周 ROI）；品质巡检为第二场景
