## 一、卡 1：交付物版式（对应问题 ①）

### 症状（用户原话）
「内容操盘手要对给我的产出物做视觉优化，现在输出的文档等内容的可视化太差了，没有可阅读性，也看不出重点，全是大段文字」

### 根因判断（不是「模型不会排版」，是没有契约）
- `agents/content-operator.md` 有「content-plan 六段」结构与禁词表，**但没有一条规定产出物的版式**；
- 没有任何机检在检查「这份 md 能不能被人 5 秒读出重点」；
- 于是模型每次都按训练分布自由发挥 → 大段文字。

### 修法：版式契约 + 可执行 lint

新建 `docs/product/DELIVERABLE_STYLE.md`（六条硬规格，可机检）：

| # | 规格 | 反例（必红） |
|---|---|---|
| S1 | 首屏必须有一张「结论卡」：结论 ≤40 字、依据条数、下一步、风险各一行 | 开头就是背景介绍 |
| S2 | 任一自然段 ≤120 字；连续 3 行无标点/无结构视为失败 | 一段 400 字 |
| S3 | 每个二级标题下 ≤5 条要点，超出必须拆小节或转表格 | 一个标题下 20 条 |
| S4 | 全文至少 1 张表 或 1 个编号清单（二者其一） | 纯散文 |
| S5 | 数字必须带单位与口径；没有数字写「未测」，不许写「显著提升」 | 「效果很好」 |
| S6 | 结尾必须有「下一步 / 待你决策」两行 | 结尾是「以上」 |

可执行载体：`tools/style_lint.py`
- 输入 md → 输出 `{ok, violations:[{rule, line, snippet}]}`
- 六条各实现为纯函数，**不许用 LLM 判**
- CLI：`--min-level error|warn`、`--json`、`--fix-hint`

机检（负例必须红）：`tests/test_style_lint.py`
- 6 个反例 → 必须每条命中对应规则号；
- 1 份合格样例 → 必须 `ok=true`；
- **故意造假测试**：把合规文件里的表格删掉 → S4 必须红；把段落拼成 400 字 → S2 必须红。

回灌：`agents/content-operator.md` 增「交付物版式（S1–S6）」段 + 「生成后必须自跑 style_lint，违规先改再交」。

工时：1 天（lint 0.5d + 测试 0.3d + SOUL 更新 0.2d）。

## 二、卡 2：交付闭环（对应问题 ②）

### 症状（用户原话）
「工作助手要把最终产出物发给我，但是目前团队停止工作后，工作助理并没有把最终的产出结果推给我，就算推给我了也是不全的」

### 根因拆三层（都要修，缺一层还是不全）

| 层 | 缺什么 | 证据 |
|---|---|---|
| 契约层 | 没有「任务收尾四步」：出卡 → 存产物 → 生成交付摘要 → 推送 | `agents/` 里只有 content-plan，没有 deliverable 契约 |
| 接口层 | 没有交付物登记/推送接口；`artifact_manifest.py` 只清单不推送 | `grep deliverable server/app.py` 0 命中 |
| 事件层 | 没有 `bot_team_deliverable_published`，飞轮看不到「交没交」 | `runtime/events.jsonl` 无此事件 |

### 修法：三件

1. **`POST /api/tasks/<id>/deliverable`**（新增）
   - body：`{summary, files:[...], next_actions:[...], risks:[...], is_demo}`
   - 落 `runs/<id>/deliverable.md`（按 S1–S6 版式）+ `deliverable.json`
   - 调 `style_lint`：**不合规直接 400**，返回违规清单（不许静默通过）
   - 发 `bot_team_deliverable_published`（payload：files 数、sha256 列表、is_demo）
2. **`POST /api/tasks/<id>/notify`**（复用现有 `notify_signed` 链路）
   - 把 deliverable 的**摘要 5 要素**（结论/证据/风险/下一步/文件清单）推 IM
   - 推送失败必须落 `push.json` 的 `failed` 状态并返回 502（**禁止静默**——这是上次「推了但不全」的根因）
3. **工作助理契约**：`agents/jobs.md` 加「收尾四步」，缺任一步视为未完成

机检：`tests/test_deliverable_publish.py`
- 缺 deliverable 就 publish → 400；
- 版式不合规 → 400 且带 rule 号；
- 推送失败 → 502 + `push.json.state=failed`（不许 200 假成功）；
- 成功 → `deliverable.md`/`.json`/事件三件齐 + 摘要 5 要素齐。

工时：1.5 天（接口 0.5d + 推送 0.3d + 测试 0.5d + SOUL 0.2d）。

## 三、卡 3：飞轮自身的零期诚实（对应问题 ③）

### 我发现的三个真问题

1. **采集有量无质**：23 条时间线里 `memory_change` 占绝大多数，`card_issued=0` —— 说明事件定义跑到真实使用前面了，指标全 null。
2. **周报会把零期当成绩**：`flywheel_weekly` 样本 <8 出 null 是对的，但**没有「零期声明」**，读的人容易误读成「一切正常」。
3. **判据 M0–M7 里 M4/M7 依赖真实签字与回填**，现在永远红——红着不丢人，**装作绿才丢人**。

### 修法
- 周报加 `phase: "zero-baseline"` 字段 + 第一行大字：「当前无真实样本，所有效率指标不可用」；
- `timeline.jsonl` 增 `signal_quality`：「本周 N 条里 M 条是系统自述（memory_change/self-record），有效业务信号 K 条」；
- 判据页把「红」的原因写死（M4 需真实签字 / M7 需 T+7），**给红线一个 deadline**，到点没绿就承认没跑起来。

工时：0.5 天。

## 五、反证信号（出现就停手重想）

- `style_lint` 上线后，真实交付物 100% 违规 → 规格定错了（S2 的 120 字可能太紧），先改规格不改模型；
- deliverable 接口做完了，Bot 一次都没调 → 契约写进了文档但没进 SOUL，等于没写；
- 推送成功率 <80% 且失败原因都是凭据/网络 → 是通道问题不是产品问题，别在契约上找补。

## 六、不做什么

- 不做第二个前端/看板（Tobs 面板就是门面）；
- 不为了让 M4/M7 变绿去手写假签字/假回填（造假成本 30 分钟，代价是整条飞轮作废）。

## R2-F 反哺口（2026-11-04 修正，按聚鲸工作流 §四 四齿）

老板裁定：**不是「有产物就回流」，回流必须走晋升与退役机制**。故 F4 的实现口径改为：

| 齿 | 本项目落法 | 载体 |
|---|---|---|
| 信号 WAL | 每条修正/证伪/反馈/事故记一行（append-only，带 clause 锚点） | `runtime/wal.jsonl`（`tools/flywheel_promote.py add`） |
| 积累 | 同 `(kind, clause)` 达阈值（默认 3）才成**候选**；候选≠同类，必须打印同类性三问 | `promote-check` |
| 落地（棘轮） | 人工回答三问 + 指定落点（`soul / pack_threshold / reminder_policy / model_route`）才 `promote`；只产出提案，**不自动改 SOUL/pack 文件** | `promote` |
| 控制 | 人类确认点；退役需 `falsified / idle / superseded` + 证据 | `retire` |

铁律三条（已写进工具，违反即 rc=1）：
1. 无 `clause` 不记账（没锚点的信号无法聚类，等于没记）
2. 三问没答完不许晋升；晋升必须指定落点
3. 退役必须有证据（证伪的实验号 / 空转的观测区间），不许凭感觉删条款

**运行节奏**：周报时跑 `check`（列候选）→ 人有空时 `promote` 一条 → 落地后把改的文件行写回 `applies_to`；连续两轮无消费的条款走 `retire(idle)`。
