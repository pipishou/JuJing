## 1. 场景定位

这是**第二场景**（备选），不是首单。个人工作任务管理首单通过后，再用它验证真实工厂数据。

先做 **品质巡检** 的原因：

- 已有 `packs/quality_inspection` v1.0.0（10 因素、六维评分、硬护栏）
- 已有 `tools/ingest_inspection_data.py`（事件级台账 → 业务日聚合）
- 已有 `tools/inspect_attribution.py`（rule_based 统计归因，不把 LLM 塞进归因链路）
- 补料率归因是旗舰场景，但 11 因素、数据面更宽，首单先不碰

如果只能拿到补料率数据，告诉我，我改用 `packs/manufacturing` 的 11 因素合同。

## 2. 数据形式

- 一个 Excel（`.xlsx`，第一张表）或 UTF-8 CSV
- **一行 = 一条巡检/缺陷事件**，不要预先按天汇总
- 不要合并单元格；不要加小计行；不要删空行之外做任何清洗
- 空值保留为空，不要补 0、不要填“无”

## 3. 必需列（10 列，列名要一致）

| 列名 | 含义 | 空值会影响什么 |
|---|---|---|
| 业务日 | 事件所属业务日（08:00 切日） | 不允许为空；为空的行无法归日 |
| IPQC人员 | 巡检员姓名或代号 | `inspector_count` 变少 |
| 机台号 | 机台编号 | `machine_active_count` / `top_machine_share` 偏差 |
| 产品型号 | 产品型号 | `product_active_count` 偏差 |
| 产品名称 | 产品名称 | 仅用于明细展示 |
| 缺陷描述 | 缺陷现象原文 | 仅用于明细展示 |
| 问题类型 | 缺陷分类 | `defect_type_count` / `top_defect_type_share` 偏差 |
| 责任人 | 责任人或代号 | 仅用于明细展示 |
| 是否退货 | “是” / “否” / 空 | 空值不补；退货类指标只做描述性对比 |
| 照片数 | 该条记录的照片数量（数字） | >0 才算有照片证据 |

## 4. 时间窗口

需要连续 **27 个业务日**：

- **T**：最近 7 个业务日（要归因的窗口）
- **T-30**：T 之前 20 个业务日（基线，算 μ±2σ 控制带）

例如 T=2026-10-12~2026-10-19，则基线=2026-09-17~2026-10-11。
窗口由数据实际日期决定；缺日会在 `meta` 里披露，不补数。

## 5. 脱敏

- 人名、机台号、产品型号都可以换成代号，但**同一实体前后要一致**
- 不要放客户名、供应商报价、工资、身份证、联系方式
- 真实文件只放本机 `inbox/`，不进 git、不发公开渠道

## 6. 我会跑什么

```powershell
python tools/ingest_inspection_data.py `
  --input "inbox\巡检台账.xlsx" `
  --base-start <基线起> --base-end <基线止> `
  --t-start <T起> --t-end <T止> `
  --outdir runs\<任务号>\data

python tools/inspect_attribution.py `
  --data-dir runs\<任务号>\data `
  --output runs\<任务号>\result.json
```

产出：

- `inspection_T.json` / `inspection_T30.json`（日级 10 因素）
- `inspection_detail_T.json` / `inspection_detail_T30.json`（事件级明细）
- `result.json`（snapshot / factorTable / attribution / advice 四段）
- 后续：评分卡 → 审批门 → 签字 → 交付卡

## 7. 场景验收

- 数据合同通过（缺列/非法日期/退货值域/照片数非数字会直接报错）
- T 窗口每天都有记录；否则只能出“数据不足，不可归因”，不硬编结论
- 每条结论能回指到具体日期、机台、问题类型
- 交付卡上写明数据 SHA256、窗口、空值披露、置信/不可归因项
- 签字人必须是业务负责人；不签不归档

## 8. 时间预期

给文件后 **30–60 分钟**出第一版可复核结果；归因是否正确由数据决定，不承诺“一定找到原因”。如果数据不够，我会直接说“不可归因”，不凑结论。
