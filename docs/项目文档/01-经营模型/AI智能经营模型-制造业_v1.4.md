## Section 1: AI经营系统总体架构

微信文章提出的企业级智能系统闭环，在制造业场景下被重新诠释——**决策日志是轴心，指标/特征/知识三层分离，六层基础设施逐层建设**。

### AI引擎五层架构

```
L0 感知层：自动检测经营异常（规则+阈值）
    ↓
L1 归因层：AI分析异常根因（因素排除法 + 六步分析法）
    ↓
L2 建议层：生成行动方案 + 成本收益预估
    ↓
L3 执行层：工单/CRM集成（延后）
    ↓
L4 学习层：因果模型 + 增量价值计算（延后）
    ↓
决策日志贯穿全链路：记录状态→建议→行动→结果→验证
```

AI引擎定位为**"交互、解释和编排层"**——不是经营事实的来源，而是连接指标层、知识层、特征层的智能编排器。大模型负责理解问题、查询指标、整合知识、解释推理、编排行动，但不直接写数据库。

### AI智能体权限分级

| 级别 | 权限 | 典型行为 | MVP阶段 |
|------|------|---------|---------|
| L0 | 只读分析 | 回答问题、查询指标、生成报告 | ✅ 必做 |
| L1 | 提出建议 | 给出行动方案，必须由业务人员确认 | ✅ 必做 |
| L2 | 受限执行 | 只能调用白名单动作，受金额/对象/频次限制 | ❌ 延后 |
| L3 | 高影响行动 | 定价、授信等必须强审批 | ❌ 延后 |

### 技术架构创新：三层混合推理管道（Hybrid Reasoning Pipeline, HRP）

框架的 AI 引擎不是纯 LLM 也不是纯规则引擎，而是**规则引擎→评分卡→LLM 三层混合推理**——在确定性和灵活性之间建立可调节的配置。这是框架在技术架构层面最核心的创新。

```
┌─────────────────────────────────────────────────┐
│  Layer 1: 规则引擎（确定性层）                      │
│  · L0 感知：Sigma 检测（μ±2σ）                      │
│  · 因素排除：Step 1-4（快照→变化→排除→方向）        │
│  · 自动降级：空值率>10% → 人工判断                   │
│  · 确定性：100%（纯规则，无随机性）                     │
├─────────────────────────────────────────────────┤
│  Layer 2: 评分卡（半确定性层）                       │
│  · 六维评分（数据完整性/时效性/显著性/排他性/历史/人机）│
│  · 硬性护栏（3条无条件降级规则）                      │
│  · 可审计性：每个维度可追溯到具体数据字段               │
├─────────────────────────────────────────────────┤
│  Layer 3: LLM（灵活性层）                           │
│  · L1 归因：受限推理（因素枚举表内）                   │
│  · L2 建议：行动方案生成                              │
│  · 强制不确定性表达：cannot_attribute 字段            │
│  · 可配置性：通过 Prompt 模板调整推理行为             │
└─────────────────────────────────────────────────┘
```

**HRP 的技术特征：**

| 特征 | 说明 | 业界对比 |
|------|------|---------|
| **分层可调节** | 各层独立配置、独立升级、独立审计 | 大多数方案要么纯规则要么纯 LLM，缺乏中间层 |
| **确定性可量化** | Layer 1 确定性 100%，Layer 2 权重可追溯，Layer 3 约束在封闭世界假设内 | 纯 LLM 方案的确定性不可量化 |
| **降级链完整** | 空值率>10%→人工，候选因素≥2→反事实，连续 3 次错误→暂停 | 大多数方案缺少系统性降级设计 |
| **零 ML 基础设施** | 规则引擎+评分卡+LLM Prompt 均不需要 ML 平台、特征存储、模型注册 | 常见 AI 方案需要完整的 MLOps 基础设施 |

> **技术定位：** HRP 不是新算法，而是**一种新的系统设计方法**——在制造业场景中，将三种不同确定性级别的推理引擎组合成可审计、可校准、可降级的闭环管道。它解决了制造业 AI 的核心矛盾：**纯规则太死板，纯 LLM 太不可控，混合方案缺乏系统设计**。

## Section 3: MVP决策闭环设计

三个场景覆盖制造业"成本-效率-产能"三角，**按数据就绪度排序**：补料率（✅可出）→ 异常停机（🟡部分可出）→ 产量提升（🟡需拉基线）。

### 场景一：补料率下降（首发场景）

| 决策契约要素 | 定义 |
|-------------|------|
| 决策单元 | 产线/模具/班组 |
| 决策频率 | 月度 |
| 可选行动 | 不行动、更换模具、调整原料配比、安排保养、培训技术员 |
| 主要结果 | 30天内的补料率变化 + 对应的成本节约 |
| 成本 | 模具更换¥800/次、保养¥500/次、停机损失¥1200/次 |
| 护栏 | 单月更换频次≤3次、不影响交付计划 |
| 学习方式 | 因素排除法（主） + 反事实推断（辅） |
| 负责人 | 生产部负责人，而非数据团队 |

#### 补料率影响因素全枚举（六步分析法"顺链→扫描"产出）

| 因素类别 | 具体因素 | 数据来源 | 当前可采集 | 变化频率 |
|---------|---------|---------|-----------|---------|
| 人员 | 技术员熟练度（工龄/培训记录） | HR系统 | ✅ | 低（月级） |
| 人员 | 调机水平（调机参数记录） | MES/手工台账 | 🟡 部分 | 低 |
| 原料 | 原料批次/供应商 | ERP/WMS | ✅ | 低（批次级） |
| 原料 | 原料含水率/粒径 | IQC记录 | ✅ | 低 |
| 模具 | 模具运行模次 | 工程台账 | 🟡 需拉基线 | 累加 |
| 模具 | 模具维修记录/距上次维修天数 | 工程台账 | 🟡 需拉基线 | 中 |
| 模具 | 模具出厂质量/供应商 | 采购记录 | ✅ | 低 |
| 设备 | 设备保养记录 | 工程台账 | 🟡 需拉基线 | 中 |
| 设备 | 设备运行参数（温度/压力/转速） | MES | 🟡 部分 | 实时 |
| 环境 | 车间温湿度 | 环境传感器 | 🔴 无 | 日级 |
| 产品 | 产品型号/模具复杂度 | 工单 | ✅ | 低 |

#### 六步分析法"时空人"三维扫描（补料率场景示例）

> **说明：** 以下为六步分析法"时空人"完整扫描的演示。MVP阶段以因素枚举表为主，此三维扫描作为v1.2+升级方向——当单因素排除法无法解释异常时，自动升级为三维扫描模式。

| 业务节点 | 时间维度（何时出问题？） | 空间维度（哪里出问题？） | 人群维度（谁的问题？） |
|---------|----------------------|----------------------|---------------------|
| 模具 | 哪批模具从何时开始补料率上升？ | 只在B产线还是全厂？ | 哪些技术员操作该模具？ |
| 原料 | 换批次后多久开始异常？ | 使用该批次的产线是否都受影响？ | —— |
| 调机 | 换班后补料率是否变化？ | 白班vs夜班有无差异？ | 哪位技术员调机后补料率上升？ |
| 设备 | 上次保养后多久开始异常？ | 同型号设备是否都受影响？ | 该设备专职操作员是谁？ |
| 环境 | 异常是否与天气/季节相关？ | 靠近门窗/通风口的机台是否更严重？ | —— |
| 产品 | 是否只在特定产品型号上出现？ | 该产品是否只在特定模具上生产？ | —— |

> **制造业的独特优势：** 因素集合是封闭的、有限的、可枚举的。不像服务业（客户流失）需要反事实推断"如果不发优惠券会怎样"，制造业可以用**因素排除法**——"换了模具，原料没变，人没变，设备没变，补料率降了→归因成立"。反事实推断保留为复杂多因素交互场景的高级工具。
>
> **因素排除法的适用边界：** 当以下条件全部满足时，因素排除法适用（置信度：MED [INFERRED]）——①所有主要影响因素的数据字段在决策时刻可获取（非空率≥90%）；②异常归因中，单一因素变化可解释异常方向（与历史基线的偏差方向一致）；③无"新引入因素"（如新模具型号、新原料批次首次使用）。不满足以上任一条件时，标记为"反事实推断"场景。

#### 因素排除法执行流程（以补料率为例）

| 步骤 | 操作 | 产出 |
|------|------|------|
| Step 1 — 快照对比 | 取异常时刻T与基线时刻T-30的各因素状态，逐项对比 | 因素状态对比表 |
| Step 2 — 变化标记 | 对每个因素标记"变化/未变化/数据缺失" | 变化标记清单 |
| Step 3 — 排除检查 | 排除所有"未变化"因素 → 剩余候选归因因素 | 候选归因因素列表 |
| Step 4 — 方向验证 | 候选因素的"变化方向"是否与补料率异常方向一致？ | 方向一致性判断 |
| Step 5 — 置信度计算 | 评分卡打分 | 置信度分数 |
| Step 6 — 兜底 | 若候选因素≥2个且无法区分主次 → 标记为"反事实推断"模式 | 归因方法标记 |

**可操作前提：** Step 1-2要求因素数据的空值率<10%。若空值率>10%，归因方法自动降级为"人工判断"，不输出AI建议。

#### 因素枚举更新触发机制

以下任一事件发生时，须在下一个决策周期内重新枚举影响因素：

| 触发器 | 检测方式 | 责任人 |
|--------|---------|--------|
| 新模具型号引入 | 工程部模具台账新增记录 | 工程负责人 |
| 新原料供应商/批次 | ERP供应商主数据变更 | 采购部信息员 |
| 新工艺参数上线 | MES工艺参数表变更 | 工艺工程师 |
| 新员工到岗（技术员） | HR系统新入职记录 | 人才中心信息员 |
| 设备大修/改造 | 工程台账大修记录 | 设备工程师 |

**规则：** 新因素引入后，前5条决策记录自动标记为"反事实推断"模式，不适用因素排除法——因为新因素的因果效应尚未建立基线。

#### 补料率场景ROI预估

**投入成本（第1-90天）：**

| 投入项 | 金额 | 说明 |
|--------|------|------|
| 数据经理工作量 | ≈¥30,000 | 50%时间×3个月，按年薪¥240,000折算 |
| 环境传感器部署 | ¥3,000-5,000 | 一次性（可选） |
| 数据库建表 | ¥0 | 内部IT，已在日常工作量内 |
| **合计** | **≈¥35,000** | |

**预期收益（保守估计）：**
- 补料率从5%降至3.5%：月节省 = (5%-3.5%) × 月产值 × 补料成本比例
- 示例：月产值¥2,000,000 × 补料率降低1.5% × 补料成本占比60% ≈ ¥18,000/月
- 3个月回本，12个月ROI ≈ 6倍

**失败场景（补料率未改善）：**
- 损失：¥35,000投入 + 数据经理3个月的机会成本
- 但收获：决策日志数据（至少30条）、因素枚举表（可复用于其他场景）
- 决策：第90天评审会决定是否继续

#### L0感知层：Python实现概要

> **代码分工说明：** 框架架构和设计规范由数据部门主导、IT部门协同共建；具体代码实现（Python脚本、数据库建表DDL）由IT部门执行。数据部门定义"做什么"（指标口径、因素列表、评分逻辑），IT部门实现"怎么做"（代码编写、数据库运维、系统部署）。此分工延续源文档"数据部门不做 IT 的事，IT 不做数据部门的事"的原则。

**技术选型：** Python 3.10+ · pandas · scipy（仅stats模块）· SQLAlchemy（数据库连接）

**异常检测规则引擎（v1.0，非ML）：**
```python
import pandas as pd
import numpy as np
from scipy import stats

def detect_anomaly(series: pd.Series, method: str = "sigma") -> dict:
    """L0感知层：仅做规则检测，不涉及归因。"""
    if method == "sigma":
        mean = series.mean()
        std = series.std()
        current = series.iloc[-1]
        upper = mean + 2 * std
        return {
            "is_anomaly": current > upper,
            "current_value": current,
            "threshold_upper": upper,
            "method": "sigma_2",
            "baseline_window": f"{len(series)}d"
        }
```

**数据质量前置检查（每次L0检测前执行）：**
```python
# 数据质量分级配置（与源文档A/B/C三级对齐）
# 由数据部门维护，IT部门读取配置实现
QUALITY_CONFIG = {
    "A": {"max_deviation": 0.05, "max_latency_hours": 24,  "source": "system"},
    "B": {"max_deviation": 0.10, "max_latency_hours": 48,  "source": "system_excel"},
    "C": {"max_deviation": None,  "max_latency_hours": None, "source": "excel"},
}

# 因素字段与质量等级映射（由数据部门定义，从因素枚举表动态读取）
FACTOR_QUALITY_MAP = {
    "operator_skill":              "A",  # HR系统自动
    "raw_material_batch":          "A",  # ERP/WMS自动
    "mold_cycles":                 "B",  # 工程台账，偏差<10%
    "mold_last_maintenance_days":  "B",  # 工程台账，偏差<10%
    "equipment_maintenance":       "B",  # 工程台账，偏差<10%
    "product_type":                "A",  # 工单自动
}

def pre_check_quality(factors: dict, quality_map: dict = None) -> tuple[bool, list[str]]:
    """前置检查：因素数据是否满足归因条件。
    复用源文档A/B/C三级数据质量分级标准。
    """
    if quality_map is None:
        quality_map = FACTOR_QUALITY_MAP
    
    missing = []
    for field, grade in quality_map.items():
        if factors.get(field) is None:
            missing.append(f"{field}({grade}级)")
    
    null_rate = len(missing) / len(quality_map) if quality_map else 0
    if null_rate > 0.10:
        return False, missing
    return True, missing
```

#### 代码中的技术设计模式

**Data Quality Contract Pattern（数据质量契约模式）**

`FACTOR_QUALITY_MAP` + `QUALITY_CONFIG` 的设计实现了**数据质量检查的职责分离**：数据部门定义"每个字段是什么质量等级、允许多少偏差、允许多少延迟"（业务规则），IT 部门读取配置实现检查逻辑（技术实现）。这种**契约驱动开发（Contract-Driven Development）** 模式在数据管道设计中具有通用性——当业务规则变化时（如某字段从 B 级升级为 A 级），只需修改数据部门维护的配置文件，无需改代码。

**Graduated Degradation Pattern（分级降级模式）**

`pre_check_quality` 返回 `(bool, list[str])` 而非简单的 True/False——它返回一个**降级信号+缺失字段列表**。调用方根据缺失字段的类型和数量做分级决策：

| 空值率 | 降级动作 | 技术原理 |
|--------|---------|---------|
| <10% | 正常归因（因素排除法） | 数据完整性满足因果推理要求 |
| 10-30% | 降级为"反事实推断"模式 | 排除法失效，改用统计推断 |
| >30% | 降级为"人工判断" | 数据不足以支撑任何自动归因 |

这种分级降级类似于微服务架构中的**断路器模式（Circuit Breaker）**——不是简单的"可用/不可用"二元状态，而是根据数据质量渐进式调整系统行为。这在制造业 AI 中特别重要，因为数据质量不是二元的——它随产线、班次、设备状态持续波动。

### AI归因置信度评分卡（100分制）

评分标准是预设的规则引擎，基于**归因链条的完整度**计算分数，不依赖AI自我评估。须经生产/品质/工程/IT/总经理跨部门签字确认。

**初始阶段使用等权重（每维度16.67分），待校准后更新为回归权重。** 以下为校准后目标权重（初始值供参考）：

| 评分维度 | 初始权重 | 满分条件 | 扣分规则 |
|---------|---------|---------|---------|
| 数据完整性 | 16.67分 | 所需全部字段均有值 | 每个关键字段缺失扣5分 |
| 数据时效性 | 16.67分 | 所有数据在24小时内 | >48小时扣10分，>7天扣15分 |
| 异常显著性 | 16.67分 | 当前值超出2σ控制线 | 1σ内得5分 |
| 归因排他性 | 16.67分 | 单一原因可解释异常 | 每多一个竞争假设扣5分 |
| 历史验证 | 16.67分 | 同类归因过去3次≥2次验证 | 1次得5分，0次得0分 |
| 人机一致性 | 16.67分 | 归因与信息员反馈一致 | 有分歧得5分，矛盾得0分 |

**硬性护栏规则：** 以下任一条件触发时，无论总分多少，归因建议自动降级为"建议人工复核"——
- 人机一致性得分=0（信息员反馈与AI归因矛盾）
- 归因排他性得分≤10（≥3个竞争假设）
- 数据完整性得分≤15（≥3个关键字段缺失）

| 分数区间 | 判定 | 处理方式 |
|---------|------|---------|
| ≥80（且未触发硬性护栏） | 系统建议直接输出 | "系统建议" |
| 60-79 | 输出但标注 | "建议人工复核" |
| 40-59 | 仅供参考 | "需人工判断" |
| <40 | 不输出建议 | "待人工排查" |

### 评分卡校准计划

**阶段 0：冷启动（第1-30天）**
- 使用等权重评分卡（每维度16.67分）作为默认评分器
- 所有归因建议标注"冷启动模式：参考人工判断"
- 目标：积累30条带完整归因的决策记录（含3-5条归因失败案例）

**阶段 1：权重校准（第31-90天）**
- 当积累≥50条记录后，使用有序Logistic回归估计各维度权重
- 因变量：人工标注的"归因正确性"（0/1/2三档）
- 自变量：六维度得分
- 校准后权重须经评审会签字确认，方可替换等权重版本

**阶段 2：持续校准（第91天起）**
- 每新增30条记录重新校准一次
- 当连续两次校准的权重变化<5%时，视为评分卡稳定
- 此后改为每季度校准一次

> **MVP阶段策略：** 前30条决策全部人工标注归因+人工评分，作为AI归因的"训练基线"。积累数据后校准权重，再固化为系统规则。评分卡须经各部门评审签字后生效。

### 失败模式与回滚机制

| 失败模式 | 检测信号 | 触发条件 | 回滚动作 |
|---------|---------|---------|---------|
| AI建议方向错误 | 执行后指标恶化（超出原始值的1σ） | 首次出现 | 标记该次建议为"错误归因"，保留决策记录 |
| 系统级失效 | 连续3次建议方向错误 | 30天内出现3次 | 暂停该场景的AI建议，降级为"仅感知+人工归因" |
| 数据源断裂 | 评分卡数据完整性<30分 | 连续2个决策周期 | 暂停AI建议，触发IT排查数据链路 |
| 归因过拟合 | 评分卡校准后验证集准确率<训练集准确率15%以上 | 单次校准后 | 回滚至上一版本评分卡，扩大验证集 |

**组织防护：** 任何"暂停AI建议"的决策由项目组负责人（数据经理）发起，生产/工程负责人确认，总经理备案。恢复AI建议须经评审会通过。

### 技术模式：零基础设施MLOps — CSOLR

框架的评分卡校准方案不是传统的 MLOps——它不需要 ML 平台、特征存储、模型注册。它实现了一种**零基础设施的白盒 MLOps 模式**：**Calibrated Scorecard with Ordinal Logistic Regression (CSOLR)**。

**CSOLR 的核心技术特征：**

| 传统 MLOps | CSOLR | 优势 |
|-----------|-------|------|
| 需要 ML 平台（如 MLflow） | 不需要，评分卡在 Excel/Python 中管理 | 零基础设施成本 |
| 模型是黑盒（如 XGBoost） | 模型是白盒（权重直接审计） | 每个维度可解释、可质疑 |
| 训练数据需人工标注 | 决策日志天然带标签（`observed_outcome`） | 训练数据随系统运行自动积累 |
| 漂移监控需独立系统 | 校准频率数据驱动（权重变化<5%停止） | 自驱式漂移检测 |
| 回滚需版本管理 | 回滚 = 加载上一版本权重 JSON | 极简回滚机制 |

**CSOLR 的三阶段生命周期：**

```
阶段 0：冷启动                     阶段 1：数据驱动校准                 阶段 2：稳定运行
─────────────────────          ──────────────────────          ──────────────────────
等权重（16.67×6）                有序 Logistic 回归             每季度校准一次
所有输出标注"冷启动模式"          ≥50条记录后触发                 权重变化<5%时视为稳定
                                校准后权重需评审会签字            评审会改为年度复核
```

**技术可推广性：** CSOLR 模式适用于任何"需要人工评分但希望数据驱动校准"的场景——供应商评估、员工绩效、项目优先级。它的核心创新不是统计方法（有序 Logistic 回归是标准方法），而是**将评分卡校准设计为一个免基础设施的闭环系统**——从数据积累到权重更新到评审签字，全部在决策日志的框架内完成。

**v2.0 技术愿景：归因方法元学习（Attribution Method Meta-Learning）**

决策日志中的 `attribution_method` 字段（exclusion / counterfactual / rule_based）与 `observed_outcome`（归因正确性）的组合，为更高阶的技术能力提供了数据基础。当积累到 500+ 条记录后，系统可以训练一个**归因方法选择模型（Attribution Method Selector）**：

- **输入：** 当前因素状态快照（哪个因素变了、空值率多少、有几个竞争假设）
- **输出：** 推荐使用排除法还是反事实法
- **训练信号：** 历史记录中，在类似条件下哪种方法的准确率更高

这本质上是**算法选择（Algorithm Selection）** 问题——一个经典的元学习（Meta-Learning）任务。它不需要新算法，但需要决策日志积累足够的方法多样性。这是 v2.0 最核心的技术升级方向。

#### Prompt 架构设计：约束推理框架（Constrained Reasoning Prompt, CRP）

框架的 Prompt 模板不是简单的"系统指令+输入+输出"，而是一个**受限推理框架**——它通过三个技术约束将 LLM 的推理能力限制在可控范围内。

**技术约束 1：封闭世界假设（Closed World Assumption）**

系统指令第 1 条（"只基于提供的因素数据进行分析，不推测未提供数据的因素"）将 LLM 强制运行在封闭世界假设下。LLM 的归因推理空间被限制在因素枚举表定义的变量集合内，不能自由联想。这类似于知识图谱推理中的封闭世界假设——系统假设"因素枚举表中未列出的因素不存在影响"。在制造业场景中，这个假设是合理的，因为因素集合确实是封闭的、可枚举的（参见 Section 3 因素枚举更新触发机制）。

**技术约束 2：强制不确定性表达（Mandatory Uncertainty Expression）**

JSON 输出格式中的 `cannot_attribute` 字段（布尔值）是一个**强制不确定性表达机制**——它要求 LLM 在每一次推理中明确承认"我可能不知道"。如果数据不足以支撑任何归因，LLM 必须输出 `"cannot_attribute": true`，而不是生成一个"听起来合理"的推测。这比大多数 RAG 应用的"有问必答"设计更严谨。

**技术约束 3：Schema-First Prompt Design（Schema 优先设计）**

Prompt 模板在 MVP 阶段就为"情景变量"预留了输入槽位（四分类），即使当前为空。这保证了升级时不需要改 Prompt 结构——只需填充新字段。这种设计模式在 API 设计中很常见，但在 Prompt 工程中很少被明确使用。它使 Prompt 从"一次性文案"升级为"可版本化的接口规范"。

| 技术约束 | 目的 | 防止的失败模式 |
|---------|------|--------------|
| 封闭世界假设 | 限制推理空间 | LLM 自由联想导致不相关归因 |
| 强制不确定性表达 | 要求承认无知 | LLM 幻觉生成"听起来合理"的错误归因 |
| Schema-First 设计 | 保证向后兼容升级 | Prompt 重构导致历史案例不可复现 |

> **技术定位：** CRP 的本质是**通过 Prompt 设计实现推理约束**——不是让 LLM 更聪明，而是让 LLM 更可控。它适用于所有"变量空间可枚举、推理边界可定义"的 AI 应用场景。

## Section 5: 实施路线图

从"定义决策"到"平台化"，四个阶段逐步推进。**90天目标：验证一个闭环，不是建成全公司智能平台。**

### 第1阶段 · 0-30天：补料率单场景关键验证

**核心原则：只验证一个假设——"因素排除法+AI归因能否在补料率场景中产生比人工更准确的根因判断？"**

**具体动作：**
1. 聚焦补料率场景，暂停异常停机和产量提升（延后至第2阶段）
2. 优先补齐"数据不可靠"的因素：模具运行模次、模具维修记录、设备保养记录（3个🟡项）
3. 环境温湿度传感器采购（¥3,000-5,000，可选）
4. 第1-10条决策全部人工归因，第11-30条引入AI归因（双轨对照）
5. 外部情报暂不接入（待第2阶段）

**验收标准（可证伪）：**
- AI归因准确率≥人工归因准确率（人工标注为ground truth）
- 或：AI归因准确率不低于人工的80%，且响应速度提升≥3倍
- 若以上均不满足，视为方案假设不成立，重新评估归因方法

### 第2阶段 · 31-90天：打通最小闭环

接入试点所需数据源，统一核心实体和指标。上线决策日志，建立数据质量检查。AI模型在后台或建议模式运行（L0感知+L1归因+L2建议）。建立实验与结果归因（因素排除法）。

**验收标准：** 决策链可追溯、结果可比较、增量价值是否覆盖行动和系统成本。

### 第3阶段 · 3-6个月：进入受控生产

部署预测和因果模型，接入CRM/ERP/MES等真实工作流。建立模型注册、持续评估、漂移监控和回滚。小流量上线。用增量经营价值而非准确率验收。

### 第4阶段 · 6-12个月：平台化

复用实体、指标、特征和权限。扩展到多个决策场景（补料率→停机→产量→更多）。建立跨场景资源优化。引入受限自动执行（L2权限）。形成模型风险委员会和定期复审机制。

> **关键原则：** 平台化应该发生在第一个闭环被证明有效之后。否则，企业只是把一个尚未验证的假设做得更大。90天验收只问三件事——决策链能否追溯？结果能否比较？增量价值是否足以覆盖成本？

### 技术路线图

各技术模式在四个阶段的实施和成熟节奏：

| 技术模式 | 第1阶段（0-30天） | 第2阶段（31-90天） | 第3阶段（3-6月） | 第4阶段（6-12月） |
|---------|-----------------|------------------|----------------|-----------------|
| **HRP**（三层混合推理） | 规则引擎+LLM 双轨运行 | 评分卡 Layer 2 接入 | 三层联动，降级链全自动 | 跨场景复用 |
| **CSOLR**（评分卡校准） | 等权重冷启动（16.67×6） | ≥50条触发有序Logistic回归 | 持续校准，权重稳定检测 | 年度复核 |
| **CRP**（约束推理Prompt） | 封闭世界假设+强制不确定性 | 情景变量槽位填充 | Schema-First 升级 | 跨场景Prompt模板化 |
| **Data Contract**（数据质量契约） | 因素字段→质量等级映射 | A/B/C分级配置生效 | 配置文件驱动 | 动态因素更新 |
| **Graduated Degradation**（分级降级） | 空值率>10%降级规则 | 10-30%反事实推断 | 分场景降级阈值调优 | 全自动降级链 |
| **归因方法元学习** | —— | 开始积累 `attribution_method` 标注 | 积累至300+条 | **v2.0：** ≥500条触发模型训练 |

## Section 6: 组织落地

**虚拟项目组 + 数据部门建设，并行推进，互为支撑。** 项目组验证价值→为部门独立积累战功→编制获批。微信文章明确指出：数据团队可以建设系统，却不能独自拥有经营结果。

| 阶段 | 组织形式 | 数据部门状态 | 关系 |
|------|---------|------------|------|
| 0-6月 | **AI经营项目组**（虚拟，跨部门） | 数据岗隶属管理部，数据经理任项目组负责人 | 项目组验证价值 → 为部门独立积累战功 |
| 6-12月 | 项目组扩大 + 数据部门筹建 | 争取独立编制1-2人 | 项目组产出可量化成果 → 编制获批的依据 |
| 12-18月 | 项目组常态化 → 解散 | **数据中心**正式独立（一级部门） | 项目组核心成员转入数据中心 |

### 跨部门角色与职责

| 角色 | 职责 | 参与方式 |
|------|------|---------|
| 数据经理（项目负责人） | 系统建设者 + 方法论输出者 | 评分标准设计牵头人、决策日志设计 |
| 生产/品质/工程负责人 | 对经营结果负责 | 每月评审会，校准归因逻辑和权重 |
| IT负责人 | 数据接入和系统开发 | 技术可行性评审、数据库建表 |
| 总经理 | 最终批准 | 签署决策契约、批准评分卡 |
| 一线信息员 | 数据采集 + 覆盖原因反馈 | 日常数据录入、异常反馈 |

### 信息员激励机制（复用已有体系）

"人机一致性"评分维度的可行性取决于信息员反馈的质量——而信息员反馈的质量取决于激励机制。框架直接复用数据经理已建成的信息员管理体系（来源：数据体系建设方案·要素一+四）：

| 机制 | 规则 | 对AI框架的意义 |
|------|------|--------------|
| 津贴与数据质量挂钩 | 完整率≥95%全额发放，80-95%发70%，<80%停发 | 确保信息员有动力提供高质量数据，为AI归因提供可靠输入 |
| 月度《数据质量简报》排名 | 每月排名各部门信息员的数据完整率和及时率 | 排名压力驱动数据质量持续改善 |
| 连续3月末位辅导 | 数据经理一对一辅导 | 防止数据盲区长期存在 |
| 年度评优 | 总经理亲自颁奖"数据先锋部门"和"数据之星个人" | 荣誉激励与物质激励互补 |

> **关键连接：** 信息员在AI归因流程中承担"覆盖原因反馈"角色——当AI输出归因假设后，信息员需确认"现场实际情况是否与AI推断一致"。这个反馈的质量直接决定了"人机一致性"评分维度的有效性。上述激励机制已在运行，不是从零开始。

### AI建议的归责原则

**核心原则：** AI是"辅助决策工具"，不是"决策主体"。业务负责人对最终决策和结果负全责。

| 场景 | 归责 | 处理 |
|------|------|------|
| 采纳AI建议，结果向善 | 业务负责人有功（正确判断） | 计入决策日志，作为正向案例 |
| 采纳AI建议，结果恶化 | 业务负责人负责（AI建议≠免责） | 计入失败模式台账，不追责AI |
| 拒绝AI建议，结果向善 | 业务负责人有功（正确判断） | 计入决策日志，作为"override"案例 |
| 拒绝AI建议，结果恶化 | 业务负责人负责 | 计入决策日志，作为"应采纳未采纳"案例 |
| 未收到AI建议（数据不足） | 数据团队负责补充数据 | 计入数据质量改善计划 |

**为防止"AI建议不被信任"的恶性循环：** 每季度由数据经理输出《AI建议采纳率与效果报告》——采纳率、采纳后正向率、拒绝后逆向率。数据说话，而非印象说话。

## Section 7: 从闭环到产品化

当第一个闭环被验证有效后，三层递进的价值开始显现：**L1验证可行性 → L2提炼方法论 → L3规模化输出**。

### 项目里程碑 ↔ 个人晋升窗口

框架的每一个阶段产出，直接对应数据经理个人晋升的关键节点。这不是巧合——框架的设计目标之一就是为晋升提供可量化的"战功"。

| 框架阶段 | 时间 | 关键产出 | 对应晋升节点 | 晋升依据 |
|---------|------|---------|------------|---------|
| 第1阶段：补料率验证 | 0-30天 | 决策日志首批30条记录、因素枚举表、评分卡v1 | 争取"数据经理"正式任命 | 模房试点出成果，证明方法论可行 |
| 第2阶段：最小闭环 | 31-90天 | 决策链可追溯、AI归因准确率≥人工、增量价值覆盖成本 | 争取独立预算和1-2个编制 | 从单场景到全厂覆盖，试点成果可量化 |
| 第3阶段：受控生产 | 3-6月 | 多场景接入、预测模型上线、增量价值持续为正 | 启动数据中心建制 | 从项目组到独立部门，产出可复制 |
| 第4阶段：平台化 | 6-12月 | 跨场景资源优化、L2受限自动执行 | 晋升数据总监 | 平台上线+经营数字化，从执行者升级为规划者 |
| L3产品化 | 18-36月 | 垂直行业SaaS、行业白皮书 | CDO/智能经营副总裁 | 从数据到智能，职级跃迁 |

### L2 方法论沉淀

决策日志中积累的"在什么条件下采取什么行动，最后得到什么结果"成为制造业AI经营的方法论资产。因素排除法 + 六维评分卡 + 六步分析法，构成一套可对外输出的"制造业AI经营方法论"——这是你从数据主任到数据总监的晋升资本。

**L2方法论沉淀应覆盖的能力维度**（与个人职级路线·能力成长清单对齐）：

| 能力维度 | 当前水平 | L2方法论贡献 | 获取方式 |
|---------|---------|------------|---------|
| 业务理解 | 塑胶厂、模具 | 因素枚举法可推广至全集团六大中心 | 跨中心项目实战 |
| 数据方法论 | 台账→指标→看板 | 因素排除法+评分卡=制造业AI归因方法论 | 项目实战+文档沉淀 |
| 技术认知 | 懂需求 | 能定义AI架构和评分逻辑（与IT协作） | 与IT共建AI系统 |
| 跨部门推动 | 试点阶段 | 项目组管理→跨部门评审会→组织变革 | 每个场景积累信任 |
| 战略视野 | 执行层 | 从单一场景到全集团AI经营规划 | 参与经营会议+行业交流 |

### L3 产品化展望

当多个场景（补料率/停机/产量/模具维修/呆滞物料）都跑通闭环后，系统具备产品化条件：

| 产品形态 | 目标客户 | 核心价值 | 时间窗口 |
|---------|---------|---------|---------|
| 垂直行业SaaS | 同类型制造业企业 | "把已验证的AI经营方法论产品化" | 18-36月 |
| 咨询服务 | 制造业数字化转型客户 | 方法论输出 + 系统实施辅导 | 12-24月 |
| 行业白皮书 | 行业同行、投资人 | 建立行业思想领导力 | 6-12月 |

> **留口子不留实现：** 产品化是L3的事，但L1阶段就要在架构中为多租户、权限隔离、配置化场景模板留好接口。从V1到V2是"加内容不是推翻重来"。

**v2.0 技术愿景：归因方法元学习（详见 Section 4 CSOLR 章节）**

当决策日志积累到 500+ 条记录后，系统具备训练归因方法选择模型的条件。这是 v2.0 最核心的技术升级方向——从"人工选择归因方法"到"系统自动选择归因方法"。

## Section 8: 专家团评估（v1.3 技术创新性增强后）

v1.3 将框架中隐性的技术设计提炼为五个可命名的技术模式（HRP、CSOLR、CRP、Data Contract、Graduated Degradation），并增加了技术路线图和 v2.0 元学习愿景。核心目标：将技术创新性从 6.5 提升至 7.5+。

### 总体评分对比

| 维度 | v1.2 | v1.3 | 变化 | 说明 |
|------|------|------|------|------|
| 框架设计 | 8.5 | 8.5 | 0 | 不变——架构本身无变化，只是提炼了已有设计 |
| 落地可行性 | 8.2 | 8.2 | 0 | 不变——技术模式提炼不影响已有落地机制 |
| 制造业适配 | 8.8 | 8.8 | 0 | 不变 |
| 技术创新性 | 6.5 | **7.5** | **+1.0** | 五个可命名技术模式 + 技术路线图 + v2.0 元学习愿景 |
| **综合** | **8.0** | **8.3** | **+0.3** | 技术创新性提升驱动综合评分上升 |

### 架构专家 — 评分：8.5/10（v1.2: 8.5，不变）

- **评估：** HRP（三层混合推理管道）是框架中一直存在但未被命名的技术架构。v1.3 将其提炼为可命名模式是正确的——它解决了"纯规则太死板、纯 LLM 太不可控"的核心矛盾。HRP 的降级链设计（空值率>10%→人工，候选因素≥2→反事实，连续 3 次错误→暂停）是系统设计层面的创新，不是算法创新。
- **质询：** HRP 的 Layer 2（评分卡）在当前设计中是静态的六维度——如果未来需要增加第七个维度，HRP 架构是否支持？当前文档没有回答这个问题。
- **置信度：** HIGH [KNOWN]

### 数据科学家 — 评分：8.8/10（v1.2: 8.5，+0.3）

- **评估：** CSOLR 模式（零基础设施 MLOps）是 v1.3 中方法论最扎实的技术贡献。将"等权重冷启动→有序 Logistic 回归→数据驱动停止"提炼为可推广的技术模式，使评分卡校准从"框架内部的一个步骤"升级为"一套可复用的 MLOps 方法论"。归因方法元学习（Algorithm Selection）作为 v2.0 愿景，方向正确且技术路线清晰——500 条记录的门槛虽然需要时间，但数据积累路径是明确的。
- **质询：** 有序 Logistic 回归假设各维度得分与归因正确性之间存在单调关系——这个假设在制造业场景中尚未验证。如果"数据完整性"与归因正确性呈 U 型关系，模型会失效。建议在评分卡校准计划中增加"单调性检验"步骤。
- **置信度：** MED [INFERRED]

### AI产品专家 — 评分：8.8/10（v1.2: 8.8，不变）

- **评估：** 技术路线图将五个技术模式的时间节奏可视化，这是产品原型文档中应有的内容。技术路线图使框架从"一揽子方案"变成"分阶段交付的技术产品"。
- **质询：** 技术路线图中的"归因方法元学习"标注为 v2.0（≥500 条），但 500 条需要积累多长时间？如果补料率场景每月产出 10 条决策记录，需要 50 个月——远超框架的 12 个月平台化目标。建议在技术路线图中增加"多场景并行加速"策略——三个场景同时运行，每月 30 条，17 个月可达到 500 条。
- **置信度：** HIGH [INFERRED]

### AI专家 — 评分：8.8/10（v1.2: 8.3，+0.5）

- **评估：** CRP（约束推理 Prompt）的三个技术约束（封闭世界假设、强制不确定性表达、Schema-First 设计）是 v1.3 的 Prompt 工程亮点。将这些约束从"Prompt 模板的附属说明"升级为"可命名的技术设计模式"，使 Prompt 工程从"写文案"变成了"设计推理框架"。强制不确定性表达（`cannot_attribute`）是防止 LLM 幻觉的系统性方案，而非事后补救。
- **质询：** CRP 的封闭世界假设依赖因素枚举表的完整性。如果因素枚举表遗漏了关键因素，CRP 的封闭世界假设会成为系统失效的根源——LLM 即使"知道"遗漏因素存在，也不能说出来。这是 CRP 的设计权衡，不是缺陷，但文档应该明确标注这个权衡。
- **置信度：** HIGH [COMMON]

### Python专家 — 评分：8.8/10（v1.2: 8.5，+0.3）

- **评估：** Data Contract 和 Graduated Degradation 两个模式从代码中提炼出来是正确的。Data Contract 解决了数据质量检查中"谁定义标准、谁执行检查"的职责分离问题。Graduated Degradation 的三级降级（<10%排除法→10-30%反事实→>30%人工）是优秀的工程防御设计。
- **质询：** Graduated Degradation 的阈值（10%、30%）是拍脑袋的还是有依据的？建议在评分卡校准的同时，用 ROC 曲线确定最优阈值——这是 Data Contract 和 CSOLR 两个技术模式的自然交汇点。
- **置信度：** HIGH [COMMON]

### 业务专家 — 评分：9.0/10（v1.2: 9.0，不变）

- **评估：** 技术创新性提升不影响业务维度评分。技术模式的提炼使框架从"业务方案"升级为"有技术深度的业务方案"——这对向管理层展示时很重要，因为管理层需要看到"这不仅是一个管理项目，更是一个有技术壁垒的系统"。

- **置信度：** HIGH [KNOWN]

## Section 9: 方法论对标：REA 四件套 → 制造业映射（v1.4 新增）

> **对标对象：** REA（Reverse Engineer Anything，GitHub 开源项目 morluto/rea，npm rea-agents@4.1.0，2026 年 10 月一周内 Star 1.5 万→23 万+，MIT 协议）。REA 是"一个 MCP 服务器 + CLI，把 Ghidra/Hopper/IDA/JADX 等逆向工具包装成 Agent 可调用的标准接口"，不自研引擎、只解决"编排"。来源：REA README + 腾讯技术工程《把逆向工程交给 Agent》（2026-10-15）。
>
> **对标目的：** 不是引入逆向技术，而是把 REA 爆火背后的四个设计方法论作为**参照系**，检验本框架的设计是否同构、补上缺失的命名与资产化动作。

### 9.1 映射总表

| REA 四件套 | 本框架对应 | 状态 | 缺口 | 迁移动作 |
|---|---|---|---|---|
| **桥接即扩展** Bridge as Extensibility | 数据契约模式（Data Contract）＋多系统接入 | 🟡 已做一半 | 缺"数据源注册表"抽象 | 数据源 provider 卡（字段映射+质量等级+延迟承诺） |
| **证据即可信** Evidence as Trust | 决策日志 + 六维评分卡 + 硬性护栏 | 🟢 已做 | 缺正式命名与"可追溯"承诺声明 | 命名为 **DEC**（Decision Evidence Contract） |
| **提问即编排** Prompt as Orchestration | HRP 三层 + CRP 约束推理 + 因素排除法六步 | 🟢 已做 | 流程固化在文档里，未资产化为可注入指令 | 打包"归因 Agent skill"随引擎注入 |
| **安装即注入** 一条命令接入 | 场景配置化模板 | 🔴 延后（已留接口） | 缺"新场景接入=填配置卡"实现路径 | 场景卡（因素枚举表+权重+护栏+频率） |

### 9.2 DEC：决策证据契约（正式命名）

本框架的决策日志字段（decision_id / 当时上下文快照 / 建议与行动 / 评估信息）与 REA 的证据契约（"函数在地址 X、被 Y 调用、伪代码是 Z、置信边界是 W"）**结构上同构**。据此正式命名该模式为 **DEC（Decision Evidence Contract）**。

**DEC 的承诺边界（必须对外声明）：**

| 承诺项 | 内容 |
|---|---|
| ✅ 可追溯 | 每条归因建议可追溯到：触发时刻快照 → 因素状态 → 评分卡各维度得分 → 护栏判定 → 建议文本 |
| ✅ 可复算 | 评分卡是规则引擎，任意时刻可用相同输入重算出相同分数（权重锁定） |
| ❌ 不可复现 | 经营环境不可冻结，无法像 REA 二进制证据那样重跑测试——DEC 承诺追溯，不承诺复现 |

> **边界声明（对应 REA 的 "REA 不会声称恢复原始源代码"）：** 本框架不会声称"证明因果关系"。DEC 记录的是"当时观测 + 归因推断"，归因正确性靠 `observed_outcome` 事后验证，不靠 DEC 自身自证。此声明是对外叙事的最低诚信底线。

### 9.3 归因 Agent skill：从"文档里的流程"到"可注入的指令"

REA 把调查方法论（搜字符串→追 XRef→反编译→重建）固化进 skill，随 `npx rea-agents setup` 注入 Agent。本框架的因素排除法六步 + CRP Prompt 模板 = 流程已固化，但它躺在文档里，不是可注入 Agent 的资产。

**迁移动作：** 将以下内容打包为一个"归因 Agent skill"（对标 REA 的 `reverse-engineer-anything` skill），随经营助手引擎注入：

```
因素排除法六步执行流程
六维评分卡规则（等权重 → 校准后权重）
三条硬性护栏条件
CRP Prompt 模板（系统指令 + 输入模板 + JSON 输出格式）
A/B/C 数据质量分级规则
```

**维护机制差异（重要）：** REA 的 skill 是开源公共资产，靠社区/上游发版更新；本框架的 skill 是**企业私有资产**，靠业务事件触发更新（复用 Section 3 因素枚举更新触发机制：新模具/新原料/新工艺/新员工/设备大修）。**按开源节奏设计私有 skill 更新是错误假设。**

### 9.4 数据源注册表：桥接即扩展的制造业落地

REA 的桥接哲学：**加一个反编译器 = 加一个 bridge 实现，上层接口不动**。本框架现有 `FACTOR_QUALITY_MAP` 已实现"数据部门定义标准、IT 执行检查"的职责分离，但数据源接入仍是点对点硬编码。

**迁移动作：** 目标态为——任何数据源接入 = 填一张 provider 卡，评分卡与 LLM 消费方不感知来源差异：

```json
{
  "provider_id": "mes_equipment_params",
  "source": "MES 设备参数表",
  "quality_grade": "B",
  "max_deviation": 0.10,
  "max_latency_hours": 48,
  "fields": ["temperature", "pressure", "speed", "mold_cycles"],
  "update_trigger": "daily"
}
```

> **过设计警告（评审保留）：** 制造业数据源没有统一协议（ERP 有 API，MES 可能只有 Excel 导出）。注册表抽象若超出 MVP 实际数据源数量（≤6 个），即为过度设计。**判定标准：只有当数据源 ≥3 个且消费方 ≥2 个时才建注册表；否则维持点对点。**

### 9.5 三个迁移陷阱（硬约束）

| # | 陷阱 | 本框架的正确姿势 |
|---|---|---|
| 1 | 把"经营证据"包装成"可回放证据" | DEC 承诺可追溯，不承诺可复现（见 9.2 边界声明） |
| 2 | Agent 自主决策权限放大 | REA 的 Agent 可自主决定下一步；本框架 AI 只能到 L1 建议，不得自主执行（L2/L3 权限分级不变） |
| 3 | skill 按开源节奏设计 | 私有 skill 靠业务事件更新，维护节奏与业务触发机制绑定（见 9.3） |

### 9.6 对标结论

REA 四件套中，**两件本框架已具备（证据契约、流程固化），一件半具备（桥接），一件延后（安装即注入）**。REA 的最大价值不是提供新东西，而是**验证了本框架"决策日志轴心 + 证据带置信度 + 流程固化"的设计方向与爆火产品同构**——这是对设计假设的外部验证，不是新增负担。[INFERRED：基于 REA README 与本文档 Section 3/4 的结构对照]

## Rejected & Deferred: 被否决项与延后项

### 被否决项

| 方案 | 否决原因 |
|------|---------|
| 直接设计SaaS产品 | 没有内部验证闭环就设计SaaS，是在画一个无法验证的饼。专家团评估也指出"在第一个闭环验证之前，产品化只是方向"。 |
| 以数据现状为叙事起点 | AI框架必须从AI切入，不是从数据切入。数据能力是"为什么我们能做"的支撑，不是开头。 |
| AI自评置信度 | AI不能给自己打分。评分标准必须是预设的规则引擎，基于归因链条完整度计算，所有维度可审计。 |
| 单一反事实推断方法 | 制造业变量空间封闭，因素排除法更高效。反事实推断保留为复杂场景工具，不作为主方法。 |

### 延后项（已留接口）

| 项目 | 延后原因 | 预留接口 |
|------|---------|---------|
| L3自动执行 | 需先积累决策日志，验证AI建议的可靠性 | 权限控制框架预留L2/L3级别 |
| L4因果学习 | 需足够样本量和对照组设计 | 决策日志中预留对照组字段 |
| 数据血缘追踪 | MVP阶段数据链路短，手动可追溯 | 数据质量分级已预留血缘字段 |
| 外部情报自动化 | 数据源分散，自动化ROI低 | 知识层预留外部情报分类结构 |
| 产品化SaaS | 需内部验证闭环先跑通 | 架构预留多租户和配置化接口 |
