# 路由层（L0 详解）

> 定位：本 skill 的**唯一入口**。解决的问题是「链路这么长、还带经验库，AI 到底该加载哪一段」——答案不是全读，而是**三维判定 + 骨架/补丁矩阵 + 索引检索**。
> 锚点（供探针抽样）：`路由即第一动作` ｜ `加载预算判据` ｜ `形态识别` ｜ `接入协议`

## 一、路由即第一动作（两档亮牌：常驻一行 ＋ 按需全卡）

**P1.1 修订（依 D1 决策）**：识别卡不再每轮强制全量输出（＝流程税）；改为**两档**：透明度不减、成本大降。

**① 常驻一行（每次会话必出，成本≈1 行；硬要求，不可省）**

```
路由：形态=X ｜ 阶段=Y ｜ 加载 N 件 ≈Z KB ｜ 依据「用户原话」｜ 纠偏：直接说「形态不对」
```

**② 完整卡（仅三种情形展开；用户随时一句「亮卡」可拉全卡）**：判不准（`unknown`／跨阶段／多形态叠加）｜ 高风险动作前（发布·删除·授权·不可逆迁移）｜ 用户索要（「亮卡」「你怎么判的」「凭什么加载这些」）。

```
【情境识别】形态=? ｜ 阶段=? ｜ 模式=? ｜ 依据=<用户输入里的哪一句话>
【本次加载】<文件清单 + 各件体积 + 合计>（判据见 `assets/params.json#budget`）
【明确不加载】<列出被排除的同层文件，证明不是全读>
【预期产出】<交付物>  ｜  【出口判据】<怎么算做完>
【不确定项】<需用户确认的一处，一次只问一处>
```

**透明度守恒（D1）**：降频次与篇幅，不降可见性——① 一行声明**必有「依据」**（引原话）；② 「不加载」只在全卡列，但**用户一质疑加载量，必须立刻能给全卡**；③ 判定若中途变（形态／阶段／模式），**须重出一行声明**，不得静默改道。

**硬规则**：① 「依据」引原话，不得凭空推断；② 判不准就问，不猜；③ 全卡输出后等用户确认再读文件。

## 二、三维判定树

### 轴 ① 形态（决定加载哪份 `forms/*.md`）

| 顺序 | 判据 | 结论 |
|---|---|---|
| 1 | 有上游仓库 / 有版本跟随义务？ | `forked-upstream` |
| 2 | 有在役系统或存量数据 / 需平台迁移 / 含不可逆步骤？ | `legacy-migration` |
| 3 | 三者皆无 | `greenfield` |
| — | 判不准 | `unknown` → **问用户一处**，不得默认 |

> 二开且要迁移 ⇒ 加载 `forked-upstream` ＋ `legacy-migration` 两份补丁（补丁可叠加）。
>
> **在役优先（P1.1 补，修 B12）**：用户**未明示形态**时（排障／热修／「线上」话术高发），凡出现「线上／在役／已有用户／存量数据」⇒ **先记 `legacy-migration`**（按含不可逆步骤处置），澄清后再叠加 `forked-upstream`。**不得默认 `greenfield`**（它是「三问皆无」才成立的一档）；确无从判断就写 `形态=unknown（待澄清）`，比猜一个错的好。

### 轴 ② 阶段（决定加载 `stages/` 的哪一件）

| 用户话术信号 | 阶段 |
|---|---|
| 「从零做」「启动」「MVP」「新项目」 | ① 立项 |
| 「要不要做」「需求」「产品怎么定」「用户会怎么看」 | ② 需求（含产品定稿） |
| 「实现」「改代码」「批次」 | ③ 开发 |
| 「测试」「断言」「绿了没」 | ④ 测试 |
| 「上线」「发布」「部署」「能发吗」 | ⑤ 部署 |
| 「版本号」「编号」「跟上上游版本」 | ⑥ 版本管理 |
| 「线上出问题」「排查」「报错」「不回滚不行」 | ⑦ 排障 |
| 「复盘」「反思」「运营」「数据怎么样」 | ⑧ 反馈与运营 |

**一次会话可跨多阶段**（如「跟随上游发新版」= ⑤＋⑥）⇒ 加载清单可含 2 份阶段件。

**编号已对齐（2026-09-27；P2 分件化）**：上表即 `stages/` 分件号，**按号直取**（①=`stages/01-inception` … ⑧=`stages/08-operations`，索引与流转见 `stages/00-overview`；旧「按动作名定位」写法作废）；飞轮属内核，见 `self-optimization.md`。

### 轴 ③ 模式（决定加载哪些机制件与模板）

| 模式 | 触发 | 加载 |
|---|---|---|
| 开工 | 新项目/新批次启动 | roles-and-gates ＋ templates |
| 排障 | 有问题要定位 | 对应阶段 ＋ `pitfalls.md` 命中条 |
| 交付 | 要发版/交付 | 对应阶段 ＋ pitfalls 发布组（#5#6#10#16#17#20#21；**二开项目叠加 #14#18**，两组可叠加不互斥） |
| 复盘 | 会话收尾/事故后 | `mechanisms/experience-loop.md`（双循环权威件，P4 已建成，机检 kb-lint ⑨）＋ self-optimization ＋ wal |
| 评审 | 「要不要做」「方案行不行」 | roles-and-gates（G2.5 双视角） |
| 接入 | 新项目接入聚鲸 | 本文 §六 |

## 三、加载预算（判据外置 · 观测 · 铁律不设硬上限）

**判据唯一事实源＝`assets/params.json#budget`**：`target_kb`（参考目标）／`limit_kb`（观测警戒线）／`session.limit_kb`（会话观测线）。**铁律·不设硬上限（2026-09-27 用户令）**：全部数值＝**软目标观测线**——超线由 `size` 只提示不阻塞，不构成验收否决项或跨轮追压字数的债（字数门曾把 P1 两轮验收拖进死循环，见 `evolution.md` #18）。**本文不复制数值**——数值只在配置与机检输出里。

**测量方式**：`python scripts/probe_usage.py size`（逐件＋合计＋`--session` 复现会话口径）。`size` 反查四项（非零即非零退出）：① 锚点 ⊆ `params.json#clauses`；② 未复制 `params.json#drift` 禁用值、未引其已删件；③ `params.json#<键>` 真实存在；④ 配置节消费者声明**可落实**（声称机检者须指名存在的脚本/文件）。**大小超线不在非零之列**（铁律）。

| 层 | 件 | 机检观测（**逐件数值见机检输出**） | 处置（提示，非债、无时限） |
|---|---|---|---|
| L0 | `SKILL.md` | 超参考目标 | 减法机会随 P2 拆分顺带评估 |
| L1 | `stages/` 九件（P2 分件） | 单件均小 | 按号直取单件；`stages.md` 降为指针件 |
| L2 | routing／evolution／self-optimization／roles／pitfalls | 数件超参考目标 | 减法机会随 P3 评估 |
| L2.5 | forked／greenfield／legacy | 均在线内 | — |
| L3 | `knowledge/INDEX.md`＋`entries/`（P3 分层） | 索引在线内、条目单件小 | 查经验按 INDEX 定位；`knowledge-base.md` 降指针件 |
| 会话 | 见 `size --session` | 按场景清单复现 | 超观测线时按下述顺序自查并说明 |

**观测汇总**：逐件数值/清单**只出机检输出，本节不抄**（防第二口径源）；超线件不登记为债（铁律），只在评审时说明取舍。

**读法（大件）**：`self-optimization.md` **按小节读取，禁止整读**；`stages/` 已分件化（P2），按号读单件即可，`stages.md` 仅作指针。

**超观测线时的减法顺序（建议非强制，禁止靠加文件解决）**：① 查「有无同职责件」（有则改旧）→ ② 「流」下沉 `knowledge-base.md`（下沉≠删除）→ ③ 只加载命中条目 → ④ 仍超 ⇒ 在声明里向用户说明并请其收窄范围。

## 四、检索协议（经验库，L3；P3 已分层）

1. 以当前 `[形态 ＋ 阶段 ＋ 关键词]` 在 `knowledge/INDEX.md` 定位条目（按标签/形态列；关键词召回看条目正文，按 ID 打开读全文）；
2. 命中 → **只读**该条 `knowledge/entries/` 条目（七元数据判可信度，清单见 `assets/params.json#knowledge.required_meta`；溯源行核对场景）；
3. 全未命中 → 允许通读 INDEX（观测线 `assets/params.json#knowledge.index_limit_kb`）；**仍无 → `wal.py add --type lesson`**（这是新知识的入口，不是空手而归）；
4. 引用经验必须带 ID（如「依 KB-17」）——**否则探针抽不到，经验是否被用无机制可证**；
5. 真实消费了某条 → `record --clause <锚点> --off-round --evidence <证据> --source witness|machine` 留痕（off-round 不入轮转降级判定，降级只看抽检轮）。

## 五、纠偏协议（用户 5 秒纠偏）

识别卡是**给用户否的地方**，不是走过场。任一维判错，用户一句话即可纠偏：

| 用户说 | 动作 |
|---|---|
| 「不是二开」/「这就是全新」 | 改形态 → 重出加载清单（旧清单作废，不叠加） |
| 「现在是排障不是开发」 | 改阶段/模式 → 加 `pitfalls.md` 命中条 |
| 「别加载这么多」 | 按 §三 顺序压缩，并说明被砍掉的判据风险 |
| 「加不加某件」 | 走 `references/evolution.md` 扩展四问，不即兴加件 |

纠偏本身**必须落 `wal.py add --type correction --clause "references/routing.md#形态识别"`**（同一误判次数达 `params.json#wal.promote_min` ⇒ 晋升为判据修订候选）。

## 六、接入新项目协议（4 步）

1. **识别**：出识别卡（形态/规模/技术栈三问）；
2. **建档**：项目侧建 `00_docs/JUJING_PROFILE.md`（模板＝`assets/profile-template.md`；形态/规模/技术栈/红线/已激活条款——路由先读档案，免去重复识别）＋**待发版池初始化**：产品仓常驻 `PENDING_RELEASES.md`（模板＝`assets/pending-releases.template.md`；判据 `params.json#release_pool`——「发现问题」与「发版解耦」，采纳项显式攒批定期发版；机检 `probe_usage.py pool-check`）；
3. **裁剪编制**：按规模取 `params.json#team.scale_tiers` 档位（全编制门槛见同节），**不默认全编制**；编制职责见 `references/roles-and-gates.md`；
4. **挂门与首记**：确立该项目的门序列与三绿口径 → 记首条 WAL（项目名＋形态）。

> 接入不是「宣布使用聚鲸」，而是**产出上面四件可查产物**；缺任一件 = 未接入。

## 七、工具/伙伴接入（M1 记忆系统轻量版＋M2 多人共享；锚点 `伙伴接入`）

记忆＝skill 内 `knowledge/`＋`preferences/`（M3-lite 个人层）＋`data/`（2026-09-28 拍板：不建独立 git 仓库）；**分享 skill 文件夹＝分享记忆**。任何人/任何工具接入聚鲸＝三步：

1. **装**：把整个 `jujing-agent-workflow` 文件夹放进任何支持 skill 的工具（CodeBuddy／Claude Code／…）——记忆随行（条目、索引、消费留痕都在夹内）；
2. **自检亮证**：`python scripts/probe_usage.py size` ＋ `kb-lint` ＋ `selfcheck`（断言复算：把对外绝对化的事实断言跑一遍，任一 FAIL 即红；隔离临时库，真实台账零污染），全绿输出「聚鲸协作伙伴已就绪」——绿了才许开工（三绿精神的接入版；机检判据 `assets/params.json#memory`）；产品侧实例池在位者加跑 `pool-check --pool <池路径>`（待发版池机检，判据 `params.json#release_pool`）；
3. **登记 actor**（M2 多人共享）：把你的 `actor_id`＋身份描述报给记忆主人，登记进 `assets/params.json#memory.actors`——此后所有留痕（`record`／`wal add`）必带 `--actor <你的id>`，未登记/缺省即拒（准入登记是佐证 v2 跨人口径的前提，判据 `params.json#memory.actors·actor_policy`）。

双方拷贝各自生长后合并走 M2 合并协议：`python scripts/merge_knowledge.py --theirs <对方skill根>`（dry-run 默认，`--apply` 自动 zip 备份后写入；冲突人工裁决，协议见脚本 docstring）。

调用与写入判据的唯一权威＝`knowledge/README.md`（任务→优先读哪层五行路由表＋curator 三步写入协议＋M2 留痕纪律）；「换工具／分享给合伙人」在 SKILL 路由表的出口即本节。
