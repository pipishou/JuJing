# 角色编制与质量门（聚鲸工作流）

## 角色 5+2（从 10 → 7 → 5+2 的实证演进）

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **Orchestrator（主理）** | 路由、状态机、看板维护、质量门调度、向用户汇报、驱动 G0 对齐；承担架构职责（现状盘点/领域建模/拆卡） | 不写业务代码，不失全局视野 |
| **Builder（建造）** | 唯一 maker：编码/构建/自验证据；后端前端可再分但不设独立 UI（实测独立 UI 角色实效未验证） | 不自判 done；不碰数据可信度判定 |
| **Adversary（对抗审查）** | 独立上下文复核、找问题为 KPI、二次核查出具人 | 不放行自己的作业；不挑无关毛病（噪音稀释真问题） |
| **Steward（事实管家）** | 数据血缘、成本台账、证据链三区制（实测/推断/未验证）、有权阻断不可信入库 | 不写功能代码 |
| **Gatekeeper（门禁留痕）** | G1/G2/G4 执行、INBOX 模板化写入、关单留痕；机械动作尽量脚本化 | 不代用户关 decision 类卡 |
| **PM（乔布斯裁判）** | G2.5 甲方：产品正确性、砍功能、用户第一秒 | 不写实现 |
| **AI Manager（卡帕西裁判）** | G2.5 乙方：可靠性、人机回路、数据飞轮 | 不替 Builder 写码 |

> 人少时可合并，编制档位见 `params.json#team.scale_tiers`，但**三裁判点（用户终审/G2.5/Maker-Checker）不可省**。whalemementor 实测：2 人＋1 AI 执行机即够 MVP 全程。<!-- params-exempt: whalemementor 实测案例证据（当时编制），非判据值；判据见 params.json#team.scale_tiers -->

## 质量门总表（按流程序）

| 门 | 名称 | 强制范围 | 判定 |
|---|---|---|---|
| G0 | 用户前置对齐 | 用户可见卡 build 前 | 「用户可见效果」获用户 ack |
| G1 | CI 守卫（本地+会话外） | 所有代码改动 | 预检绿＋会话外构建 success（含逻辑回归） |
| G1.5 | 前端实测 | 任何视觉/交互改动 | 实测脚本＋亲手点验＋非作者复验 |
| G2 | 事实纪律 | 合并前 | 六项清单（事实门/血缘/审计/幂等/零回归/上云就绪） |
| **G2.5** | 双视角对抗 | 用户可见卡合并前 | 乔布斯×卡帕西各自独立结论，任一否决即打回 |
| G3 | 二次核查 | 放行类批次 | Maker-Checker：独立上下文出具独立结论 |
| G4 | 留痕关单 | 合并后 | 看板 Done＋notes 落档＋decision 类不代关 |

序列：`inbox → assigned → [G0] → in_progress → [G1/G1.5/G2] → [G2.5/G3] → done|failed`。G0/G2.5 仅对用户可见卡强制；豁免须注明理由。

## G2.5 执行细则（硬门禁）

1. Orchestrator 调度 PM＋AI Manager，两方**各自独立**输出，格式强制：
   - **我不同意什么 / 风险在哪**
   - 乔布斯视角：用户打开第一秒会看到什么；卡帕西视角：这个东西在 1 亿次使用下会怎样
   - 用户视角断言是否附齐（卡帕西核验）
2. 任一方否决（风险未被消解）即打回，不得合并。KPI 是「找出问题」，不是放行。
3. 两方结论落卡 comment 作为合并依据；用户拥有最终否决权。
4. 判例沉淀：每次 G2.5 的否决理由与消解方式 → `data/wal.py add --type lesson`，形成产品/可靠性判例库（自优化的产品设计域原料）；对抗记录（双裁判独立结论＋判定＋沉淀）格式模板：`assets/templates.md` §5。

## 外部记忆系统（跨会话不失忆）

| 载体 | 用途 | 纪律 |
|---|---|---|
| INBOX 看板 | 任务卡全生命周期 | 每卡：用户可见效果/用户视角断言/验收标准/状态 |
| 决策台账 | 方向与商业化决策 | **只追加**；修订走证据链新行；重大决策回看日 = `params.json#governance.decision_review_days` |
| U 清单（开口项） | 未闭环事项编号追踪 | 灯号制（✅/🔶/⬜/🔴），允许长期挂着不被遗忘 |
| corrections WAL | 用户纠偏即时捕获 | 每次纠偏当天一行（日期/来源/内容/关联批次）；同类次数达 `params.json#wal.promote_min` 自动提示晋升条款 |
| implementation-notes | 非 spec 决策 | 每批次追加「做了什么/如何验证/关联卡号」 |

> 载体行/卡格式模板（INBOX 任务卡、决策台账行、U 清单行）：`assets/templates.md` §1–3，复制即用，勿另造格式。

## 授权与安全红线

- **git 铁律**：未经用户明确下令零 git 动作；授权=命令式、一次性、列明动作清单（需求单式最佳）；门槛机检兜底（待授权≠缺陷，是闸门按设计报警）。
- **升级协议**（必须写 INBOX 并 @user，不得自决）：spec 偏离／删数据·破坏性迁移／新依赖／产品方向·砍功能／AI 策略·模型选型／≥2 方案取舍／放宽测试标准；请求格式模板：`assets/templates.md` §6。
- **零依赖纪律**：新依赖=升级协议事件（案例：mo-ai M8 全期 19 卡合并零新增运行依赖）。
- **并行协作·命名空间纪律**：编号／版本号／章节号属**共享命名空间**。合并协议＝合并前 `fetch` ＋比对对方改动面；**以远端为准、本地顺延重编号并同步全部引用**（含工具中的基线常量）；**禁止** rebase/force 改写已推历史；**撞车处置留痕**（写清「哪个号现在指谁」）。完整案例见 `references/pitfalls.md#18`。

## 交接五要素（handoff）

```text
【做了什么】一句话摘要        【产物路径】绝对路径/PR/构建号
【如何验证】可复制命令        【已知问题】未完成项/风险/隐藏前提
【下一步】接收方明确动作
```

## 任务卡必填三字段（Architect/Orchestrator 产出时强制）

> 范围（P3 明示）：三字段与 G0/G2.5 的强制面＝**用户可见卡**；纯内部件走豁免通道（豁免卡注明豁免理由留痕）。 maker 本人自写自跑的绿测＝同源自审（公理 2），**不豁免**独立二次核查。

| 字段 | 说明 | 门禁 |
|---|---|---|
| 用户可见效果 | 一句话读得完（秒数判据：assets/params.json#team.assert_readable_seconds）：用户第一屏看到什么、行为有何不同 | G0，未对齐不得 build |
| 用户视角断言 | 断言条数达 `params.json#team.card_assert_min`（如「录入 X 后今日关注首条必含 X」） | 无断言禁 merge |
| 验收标准 | 技术可验收条件（状态码/字段/回归） | G2 |
