# ②b 技术方案（需求与开发之间的门）

五件套：**目标 → 关键动作 → 出口判据 → 实证 → 陷阱**；索引与流转规则见 `00-overview.md`。

> **为什么单独成阶段**（锚点`方案阶段`，2026-11 外部经验吸收）：方案阶段改方向成本最低，开发阶段发现方向错了代价最高。此前方案纪律寄生在 `03-development.md` 动作 10，只有模板没有门——细则写了、门没立，等于把最容易失真的环节放在无人检查的位置。本件立门，`03` 只留一行指针（陷阱 #9 防双写）。

## 目标

把「需求五件套」变成**可施工的方案卡**：依赖顺序无前向引用、每步可独立验证、未证假设显式列出、待确认问题清零或带风险开工。

## 进门先读（≤15 行）：阶段进门清单（锚点`进门清单`）

```bash
python scripts/kb_query.py --stage 02b
```

输出 ≤`assets/params.json#knowledge.intake_max_entries` 行的候选经验（ID｜标签｜一句话｜路径｜状态）。规则：

1. 只读清单行，**不读 `knowledge/entries/` 整目录**（预算见 `#knowledge.intake_max_lines`）。
2. 与本次方案**强相关**的条目最多展开 `#knowledge.intake_fullread_max` 条全文；其余列"相关但未展开"即可。
3. 清单为空或零命中 → 方案卡「进门知识」栏写「本阶段无可用知识」，**禁止编造引用**。
4. 真用了某条 → 收尾 `record --clause <锚点> --off-round --evidence "<怎么用的>" --source witness` 留痕。

## 关键动作

1. **进门读需求件**：`02-requirements.md` 的出口产出（可见效果／用户断言／验收标准／只有你知道的背景）与本卡逐条对齐；对不齐先退 ②，不在方案里替需求补洞。
2. **按依赖图排序**：自底向上（存储模型 → 契约/接口 → 业务逻辑 → 调用方/前端）。禁按"重要性/手感"排期；任何一步不得引用尚未在前序步骤创建的东西。
3. **垂直切片**：每步交付一条端到端可验证路径（建表＋接口＋最小逻辑＝一个切片），不"先铺三层底座再接通"；每步结束时系统应可编译、可验证。
4. **粒度纪律**：单步改动文件数 > `assets/params.json#plan.max_files_per_step`，或跨 `#plan.cross_subsystem_trigger` 个以上子系统，必须再拆。步骤标题出现"并且／同时"通常意味着它其实是两步。
5. **检查点**：每 `#plan.checkpoint_every_steps` 步插一个可验证节点（三绿／机检／人核任一），不许一口气做完再验。
6. **找茬自审**：对关键决策（跨模块修改、编译器无法验证的属性如并发安全/幂等/不变量、不可逆变更）自问 `#plan.self_audit_question`，答案写进方案卡「未证假设」栏，**每条假设同时标「校验粒度」**（类别／分片／全量）；比例、占比类结论必须分层校验，全局汇总会掩盖局部反向证据（实测把正常记录判成异常，虚高 13.7 倍）；空着＝自欺信号。
7. **待确认前置**：不确定、需人拍板的点统一收进「待确认问题」栏（产品类／技术类分开），用户逐题答（选择题＋开放题）后才进下一轮；模糊不许带进开发。
8. **关联面自检**（人的第四节点落地）：凡改动 A，必须回答「A 还被谁引用」——巡检脚本／定时任务／配置项／文档／其他调用方。答不出就列为待确认问题（真实事故类型：标签拆分需求漏改关联巡检 Skill → 入库 Bug）。

## 出口判据

1. **依赖顺序无前向引用**：方案卡「依赖顺序」节可逐行核（被引用对象均在前序步骤出现）。
2. **切片与粒度达标**：每步 ≤`#plan.max_files_per_step` 文件且可独立验证；超线步骤已拆或写明拆分理由。
3. **五个必填节齐**：依赖顺序／切片粒度／检查点位置／未证假设／待确认问题（载体 `assets/templates.md` §8，缺第 2/3/4 任一节＝方案未过审；第 4 节每行须填「校验粒度」）。
4. **待确认问题清零或带险开工**：未清零时方案卡必须写「带哪些风险开工＋谁批准」，不许静默开始编码。

> 四条均为人核判据，**不做自动评分**：加权打分门＝假门（`pitfalls.md#19`），能过分数不等于能干活。

## 实证

- 2026-11 外部经验（企业 AI 研发平台实践）：方案阶段对最终代码质量影响最大；按重要性排序的方案会让开发 AI 反复撞"步骤 2 依赖步骤 5 才创建的东西"。
- 本 skill 自身教训：`03-development.md` 曾把方案纪律写成动作 10 而不设门，导致"方案卡有模板、无出口判据"——载体在、门不在（评审 B3/B1 类问题的同型）。

## 陷阱

- 把方案写成提纲（列功能不列依赖）＝开发期返工的根源。
- 大爆炸切片（一次改 8 个文件）→ 回归面不可控（公理 1）。
- 自审栏全填"无"＝没审，不是没问题。
- 待确认问题留到开发中边做边问 → 等于让人给已完成的方案背书（`pitfalls.md#2`）。
- 用"方案已评审"当免检牌：评审只看方案卡，不看代码是否照做；照做与否由 ③ 的改动面核对（`#plan` + 回执「改动面 vs PLAN 文件集」）。
