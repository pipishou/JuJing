> 标签：测试/绿测掩盖

## 经验正文

三条同根不同形的「缺陷被掩盖/误判」判例，共通纪律＝**先解耦真值，再定归属**：

1. **断言假阴 ≠ 产品无罪**（#36）：验证脚手架自身失败（跨 wsl 边界 `docker cp` 静默失败且脚本未查返回值）会把 e2e 断言打成假阴。动作：断言失败先绕开脚手架直取产品链路真值（如 `docker exec -i … python - <` stdin 喂脚本，零注入零路径转换），确认产品真值后再判缺陷归属——防把脚手架问题误判成产品缺陷（或反向洗白）。
2. **「不产生数据」≠「没有缺陷」**（#38）：潜伏缺陷常被零数据时代掩盖（进程级 workspace 串库在计费上线即现）。动作：计费/落库/归属类新功能上线前，按 uid 全盘扫库验证落点归属，不靠单点抽查。
3. **门禁拦下的「死件」先验「真删 vs 迁移」**（#39）：上游合并工具对迁移重命名按 delete_keep 误保留→树内双实现死件。动作：源与目标文件名对不上时，以上游 wheel 解包为真值源判定「真删还是迁移」，门禁红线不绕行（--no-verify 禁令），停下取证再处置。

**为什么**：三者都是「绿/静默掩盖真缺陷」的第二形态——第一形态是测试没写（绿测掩盖死功能，公理 5 本文），本条是「测了但证据链被脚手架/零数据/工具误判污染」。防自欺红线的取证细则。
