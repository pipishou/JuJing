# 形态补丁 · legacy-migration（存量改造 · 平台迁移）

> 用法：路由判定形态=legacy-migration 时加载本件。**只写本形态在各阶段的额外动作**；阶段骨架见 `references/stages/` 分件（按号直取，索引 `stages/00-overview`）。
> 锚点（供探针抽样）：`数据不跨版本` ｜ `可恢复性前置`

## 判据（任一为「是」即本形态）

1. 存在**在役系统/存量数据**，改动会触及数据或用户的连续可用性？
2. 需要**平台迁移**（云厂商/托管方式/运行时切换）？
3. 目标状态与现状之间存在**不可逆**步骤（删数据、改配置、换域名/换鉴权）？

## 实证案例

| 项目 | 证据 | 沉淀为本件的哪条 |
|---|---|---|
| DeepTutor/whalemementor | 迁移阿里云二次评估复核；云托管部署路线核实 | §③：路线核实先于动手 |
| whalemementor 030 线上验收 | **数据不跨版本（发版即清档）判定为一号阻塞**；额度配置未注入被列为须同批处理项 | §⑤：迁移与配置变更同批 |
| whalemementor 配置面事故 | 破坏性配置变更时序（先让数据可恢复再改会销毁数据的配置） | §⑤：可恢复性前置 |

## 各阶段额外动作

| 阶段 | 额外动作 | 出口判据增量 |
|---|---|---|
| ① 立项 | 存量盘点：**在役版本/数据位置/数据量/不可失数据清单**（数据面先于代码面） | 不可失清单 ＋ 现役指纹 |
| ② 需求 | 每条改动标 **可逆 / 不可逆**；不可逆项须给恢复路径或显式接受风险 | 不可逆项 ≤ N 且各有恢复路径 |
| ③ 开发 | 迁移路线先**核实**再动手（能力边界/配额/网络/鉴权四项核实）；不做「边迁边改」 | 路线核实结论留痕 |
| ④ 测试 | **一致性断言**：迁移前后同一输入 → 同一输出（或差异有据）；存量数据抽样比对 | 一致性断言 + 抽样证据 |
| ⑤ 部署 | ① **数据跨版本/跨部署检查前置**（发版会不会清档？配置更新会不会重建？）② 迁移与配置变更**同批**（避免二次清档）③ 破坏性配置：先让数据可恢复 ④ 回滚路径必须真实可用（演练过） | 清档检查结论 ＋ 同批留痕 ＋ 回滚演练证据 |
| ⑥ 版本管理 | 迁移期间**并行命名空间**：旧线只修致命问题、新线推进；版本号与文档章节号不得与旧线冲突（陷阱 #18） | 双线命名空间无交叉 |
| ⑦ 排障 | 先判「迁移引入 / 存量固有 / 环境差异」三类根因；**旧环境=对照基线**（比 greenfield 多一份免费基线） | 根因归类 ＋ 对照证据 |
| ⑧ 运营 | 灰度与回滚窗口；用户可见影响提前告知并留痕；迁移后**复核原问题是否真消失**（防「表象修复」陷阱 #4） | 复核结论 |

## 通用强化

- **不可逆操作前置审批**：删除数据、切域名、改鉴权、换凭证 → 属升级协议七类，必须 @user。
- **成本是迁移的一等判据**（陷阱 #10）：迁移前后各记一行成本台账，避免「迁完更贵」。
- **「能力边界」先于「方案设计」**：平台不支持的能力，方案再优雅也不成立（实证：云端源码构建通道判死，产物落构建环境内部 registry，pod 恒 ImagePullBackOff）。

## 退役条件

一次性迁移完成后，若项目转为稳态运营（不再有存量约束），本件对该项目空转 → 按 `references/evolution.md` 退役或降级为知识库候选；但**判据保留**（下一个迁移项目还要用）。
